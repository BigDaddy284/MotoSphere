## Objective

No statement can give a review item a key below 1, whichever of the
names SQLite has for the key of a table the statement uses.

## Why

This puts right a defect in work that was verified (DAT-056). The
store promises that a key of the review queue is 1 or more, and two
triggers hold it: one for a new item, one for an item that is changed.
The second was written to fire after an update of the column `id`.
SQLite has three more names for the key of a table, `rowid`, `_rowid_`
and `oid`, and a statement that sets the key by one of them does not
fire a trigger that names the column. On a store at the newest schema
`UPDATE review_item SET rowid = -5 WHERE id = 5` was taken, where
`SET id = -5` was refused. The tests of DAT-056 used the name of the
column only. No store holds a review item yet, because nothing writes
one before Phase 10, so no record is wrong; but the rule did not hold
as the documents said, and the next task (DAT-067) builds more
triggers of the same kind.

## What this task is, and what it is not

- **It is** the second trigger of the keys, written anew in the model
  and by an eighteenth migration, the tests that hold it under every
  name of the key, and the documents of DAT-056 put right.
- **It is not** a change to the first trigger of the keys, which holds
  a new item: it fires for every new item, whatever the statement
  names, and the new tests show that it does.
- **It is not** a change to any other trigger. None of the others
  names a column: the planner read every trigger of the migrations.
- **It is not** a change to the eleventh migration, which made the
  trigger as it was. A migration that stores have taken is never
  changed; a planted defect that changes it is found.
- **It is not** a change to what an item is or to a command.

## Design in short

The trigger as it was (the eleventh migration, DAT-056):

    CREATE TRIGGER tr_review_item_key_stays_positive AFTER UPDATE OF id ON review_item
    WHEN NEW.id < 1
    BEGIN
        SELECT RAISE(ABORT, 'A key of the review queue (review_item) is 1 or more.');
    END

The trigger as it is from the eighteenth migration on, and in the
model:

    CREATE TRIGGER tr_review_item_key_stays_positive AFTER UPDATE ON review_item
    WHEN NEW.id < 1 AND NEW.id != OLD.id
    BEGIN
        SELECT RAISE(ABORT, 'A key of the review queue (review_item) is 1 or more.');
    END

The eighteenth migration, `hold_the_key_of_a_review_item_under_every_name`,
takes the old trigger out (`DROP TRIGGER`) and makes the new one. It
changes no table, no index and no row.

## What the trial measured and settled

- **Ten of thirteen.** The new tests name the key in thirteen ways:
  `id`, `rowid`, `_rowid_` and `oid`, each also in other capitals or
  in the marks SQLite takes around a name. With the trigger as it was,
  a key below 1 was refused under the three spellings of `id` and
  taken under all ten others: 40 of the 52 cases of the first new test
  fail there.
- **A trigger that names no column fires for every update**, whatever
  the statement names. So the new trigger says `AFTER UPDATE ON` and
  asks itself whether the key changed.
- **It asks whether the key is another than it was.** A trigger that
  fires for every update and asked only whether the key is below 1
  would refuse every change of an item that has such a key already. A
  store can hold one: an item stored before the eleventh migration
  kept its key. Such an item can still be given a note, and a key of 1
  or more, and then cannot go back; it cannot be given another key
  below 1. `NEW.id != OLD.id` says that, and tests hold each part on a
  store that was at version 10 when the item was stored.
- **The trigger asks after the row is written**, so it sees the key
  the item got. Where a statement names the key twice, SQLite takes
  the last; a test holds both orders.
- **Every kind of statement that changes an item is held**: the key
  after another column or in one list with it, `UPDATE OR REPLACE` and
  `UPDATE OR IGNORE`, a key counted from its own for every open item,
  a key from a query (`UPDATE … FROM`), and an item that is stored
  again with `ON CONFLICT (id) DO UPDATE SET`. `RAISE(ABORT)` refuses
  whatever the statement says is to be done about a clash.
- **A decided item is still told that it is never edited**, under
  these names too: that trigger fires before the update and names no
  column.
- **A new item is held under these names too.** The first trigger of
  the keys fires for every new item; six new cases store one with the
  key named `rowid`, `_rowid_` or `oid`.
- **The migration fails where the trigger it takes out is not there**,
  and leaves the store at version 17: a store whose history says 17
  and that lacks the trigger is not a store these migrations made, and
  is not passed over. A planted defect that passes over a missing
  trigger (`DROP TRIGGER IF EXISTS`) is found.
- **The migration is tried on a store that holds items**, three open
  ones, one of them with a key below 1 from before the eleventh
  migration: every table, index and trigger is there by the name it
  had, the tables and indexes are written as they were, only this
  trigger is written anew, and the items are as they were. A statement
  that sets the key below 1 by one of SQLite's own names is taken
  before the migration, which is the defect, and refused after it,
  with what was taken before left as it is: the migration puts no item
  right, because it cannot know which key an item should have.
- **The model and the migration agree**: the test of the models and
  the migrations passes unchanged, and planted defects that change one
  of the two alone are found by it.
