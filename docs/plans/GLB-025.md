# GLB-025 – The engine is told where its files are

**Phase:** 3 – Interactive 3D Earth
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** GLB-022 (merged), GLB-024 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §9, §12 and §14, `docs/WORKFLOW.md`,
`TASKS.md` ("Two tracks" and the entry of this task), `ARCHITECTURE.md`
§3, `TESTING.md` ("The engine's own files in the site"),
`frontend/site.ts`, `frontend/src/main.tsx`,
`frontend/sitebuild/engineFiles.ts`, `frontend/e2e/engine.spec.ts`

## Objective

Before the engine is first used, the application tells it the address of
its own files, built from the one place that names the site's path.

## Why

The engine of the globe fetches background scripts, programs, tables and
pictures while it runs. Since GLB-022 the built site holds them under
the folder `cesium/` of the site's path, and since GLB-024 the
development server answers them there too. The engine does not know
that. It asks for every such file beneath one base address, and left to
itself it works that address out from where its own code was loaded
(`import.meta.url`). In the built site that is a file of the build with
a name of its own, in the folder `assets/`, and the engine's files are
not beside it: every one of them would be "not found", and the globe of
GLB-002 would stay empty.

## What this task is, and what it is not

- **It is** one new module of the application,
  `frontend/src/globe/engineAddress.ts`, with the address
  (`ENGINE_ADDRESS`) and a function that tells the engine
  (`tellTheEngineWhereItsFilesAre`), and one call of that function in
  `frontend/src/main.tsx`, before anything is shown.
- **It is** the name of the folder, `ENGINE_FOLDER`, moved from the step
  of the build to `frontend/site.ts`, where the site's path is. The step
  takes it from there and hands it on under the same name, so nothing
  that imports it from the step changes.
- **It is** 16 unit tests in a new file,
  `frontend/src/globe/engineAddress.test.ts`, and 2 browser tests more
  in `frontend/e2e/engine.spec.ts`.
- **It is not** the globe. Nothing of the application loads the engine
  yet, so a visitor's browser still fetches none of its files. That is
  GLB-002.
- **It is not** a change to which files of the engine the site holds
  or to what the development server answers.

## Design in short

- **The engine's own way of being told.** The engine
  (`@cesium/engine` 26.5.0, `Source/Core/buildModuleUrl.js`) takes its
  base address from a global named `CESIUM_BASE_URL` when there is one,
  and only otherwise from where its code was loaded. It reads it the
  first time it builds the address of a file, and keeps it from then
  on. The application puts the address under that name. The name is the
  engine's; it appears in one module of the application and nowhere
  else.
- **The address is built, not written.**
  `` `${SITE_PATH}${ENGINE_FOLDER}/` ``: the site's path and the name of
  the folder, both from `frontend/site.ts`, and a last stroke, which the
  engine needs to take it for a folder. The build and the development
  server take the folder's name from the same place, so the files
  cannot be put in one place and looked for in another. Today it is
  `/MotoSphere/cesium/`.
- **A path, and no computer.** The address begins with one stroke and
  names no scheme and no computer, so a browser reads it on the
  computer the page came from. The engine asks this site and nobody
  else (`CLAUDE.md` §14).
- **Told where the application starts.** `main.tsx` calls the function
  as its first statement after what it brings in, before it looks for
  its place in the page and before it shows anything. Whichever module
  asks for the engine first, at whatever time, the address is there. No
  module of the engine reads the address while it is being loaded (the
  planner read the source: every call of `buildModuleUrl` is inside a
  function), so being first among the statements is enough.
- **A function that is called, and not a module that acts when it is
  brought in.** The lint of the project refuses an import that names
  nothing (`import './x.ts'`), with good reason: such a module does
  something nobody sees. So the module hands out a function and
  `main.tsx` calls it by name.
- **Why the folder's name moves to `site.ts`.** The application cannot
  import `frontend/sitebuild/engineFiles.ts`: that file is a step of the
  build and uses the disk (`node:fs`), which a browser has not.
  `site.ts` is already read by the build and by the tests, and has
  nothing in it a browser lacks.

## What the task left open, and what the trial settled

- **The global, or the engine's function?** The engine also has
  `buildModuleUrl.setBaseUrl(value)`. It is not used. It is not in the
  engine's type declarations, so calling it would need an assertion,
  which the project does not write. And calling it needs the engine
  loaded, and GLB-002 loads it only when the globe is shown. The global
  costs nothing and is read whenever the engine comes.
- **"Before any other code of the engine runs."** Held in three ways.
  From the text of `main.tsx`: the call is there exactly once, before
  `createRoot(`, with nothing before it but imports and comments. By
  starting the application for the test: with a place in the page, and
  without one (when it stops with its own sentence), the address has
  been told. And on the built site, in a browser: the page as it was
  built has the address under the engine's name.
- **"Nothing else in the application writes it."** Held from the text
  of every file of the application that could: its code under `src/`,
  the page `index.html`, the settings of the build and `site.ts`
  (tests are not among them). The engine's word `CESIUM_BASE_URL`, and
  `setBaseUrl`, are in the one module only; `ENGINE_FOLDER` is in
  `site.ts` and in that module only; the folder's name with its stroke
  is written out nowhere; and the function is named in the module and
  in `main.tsx` only.
- **"The engine as installed builds the address … beneath it."** The
  unit tests call the real `buildModuleUrl` of the installed engine,
  not a copy of it, for a background script, a program, a table, a
  picture of the Earth and the folder of those pictures: each address
  is on the computer of the page, beneath the folder, with nothing
  after the name.
- **What a unit test cannot show.** The trial also wrote a test of the
  engine when nobody tells it (that it then looks beside its own code).
  It could not be made honest: the engine keeps the address once it has
  read it, and the test runner gives a test no second, fresh engine
  (`vi.resetModules()` does not reach a package that is not part of the
  project's own code). The test was dropped, and nothing is claimed
  about it. For the same reason the new test file tells the engine
  before its first test: keep that line.
- **Does the site answer at the address?** That is what the two browser
  tests are for. The browser itself, from the page, fetches one file of
  each of the eight kinds by its name beneath the address the page was
  told: each is answered with the status 200, at the address the site
  has for it, with the length of the engine's file. That is the same
  question the engine will ask in GLB-002, without the engine.
