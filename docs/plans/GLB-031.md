# GLB-031 – A test of the globe has 90 seconds

**Phase:** 3 – Interactive 3D Earth
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** GLB-002 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, `docs/WORKFLOW.md`, `TASKS.md` ("Two
tracks" and the entries of this task and of GLB-030), `PROGRESS.md`
(PLAN-060), `TESTING.md` ("The browser of the globe tests" and "The
Earth in the page"), `frontend/playwright.config.ts`,
`frontend/e2e/globe/browser.spec.ts`, `frontend/e2e/globe/earth.spec.ts`

## Objective

Every browser test of the globe has 90 seconds, set once for the
project `globe`. A browser test of the other project has 30, as
before.

## Why

The browser of the globe tests draws 3D pictures in software, and a
test that waits for the Earth or reads its picture waits for that
drawing. How long that takes is a matter of the machine and of how
much of the Earth is in view.

The planner's trial of the next task, GLB-030 (the view the globe
opens with), has the whole Earth in view at every size of the screen.
It was run on GitHub's two machines twice, and with it the five tests
of GLB-002 that were there took up to four times as long on the
Windows machine: the test that takes two pictures of the stage took
6.2 and 15.0 seconds in two runs with the view the engine opens with
by itself, and 23.9 and 22.8 seconds in the two runs of the trial, of
the 30 a test has. On the planner's own machine, with two other runs
of tests beside it, a new test of that trial ran out of its 30
seconds once in 21 runs. No test of the application was wrong in any
of this: the pictures were the right ones, and they came late.

A test of the globe holds what the page shows, not how fast a machine
is. So the limit of time is raised before the view is changed, as a
task of its own: it touches the settings of the browser tests, and
GLB-030 touches the application.

## What this task is, and what it is not

- **It is** one line in the settings of the browser tests
  (`frontend/playwright.config.ts`), one new browser test that holds
  it, and one line taken out of a test that had 90 seconds of its own.
- **It is not** a change to the application: nothing under
  `frontend/src` changes, and a person who opens the page sees what
  they saw before.
- **It is not** a change to what any test holds. No assertion is
  changed, and no test is taken away.
- **It is not** more time for the other browser tests, nor for the
  waits inside a test: a test of the globe still waits at most twenty
  seconds for the Earth to be drawn (`DRAWN_WITHIN` in
  `earth.spec.ts`), and an expectation still has five.
- **It is not** a change to the limit of the Windows job on GitHub (20
  minutes, FND-057) or to the workflow.

## Design in short

In `frontend/playwright.config.ts`, the project `globe` gets one line:

    {
      name: 'globe',
      testDir: './e2e/globe',
      workers: 1,
      timeout: 90_000,
      use: { ...devices['Desktop Chrome'], launchOptions: GLOBE_BROWSER },
    },

In `frontend/e2e/globe/browser.spec.ts`, one new test among "the globe
tests":

    test('have 90 seconds each, where a test of the other project has 30', ({
      browserName,
    }, testInfo) => {
      expect(browserName).toBe('chromium')
      // What this very test has, and what the settings give each project.
      expect(testInfo.timeout).toBe(90_000)
      expect(testInfo.config.projects.map((project) => [project.name, project.timeout])).toEqual([
        ['chromium', 30_000],
        ['globe', 90_000],
      ])
    })

It asks for `browserName` so that it runs in the browser of the
project, as the test before it does; the settings are read from what
Playwright gives the test.

In `frontend/e2e/globe/earth.spec.ts`, the test that stops and starts
the engine twenty times loses its line `test.setTimeout(90_000)`, and
its comment says where the 90 seconds come from now.

## What the trial measured and settled

**What was measured** is in `TESTING.md`, "A test of the globe has 90
seconds", which the diff adds: the one pause for each opening of the
page, the one test that ran out of 30 seconds, how much more there is
to draw with the whole Earth in view, and the times of the five tests
of `earth.spec.ts` on GitHub's two machines with and without it. Read
it before the diff.

**Why 90.** It is the number the slowest test of the globe already
had: the test of GLB-002 that stops and starts the engine twenty times
was given 90 seconds when it was written. With the whole Earth in view
that test took 35.1 and 30.6 seconds on GitHub's Windows machine, and
no other test of the globe took more than 23.9 in the four runs that
were read. So 90 is between two and three times the longest time that
was seen. A larger number was not tried and nothing that was measured
asks for one.

**Why the project and not each test.** Every test of the globe waits
for the same drawing, the ones that are written later too. One number
in the settings holds for all of them, and the next task (GLB-030)
adds a file of seven tests that would have needed it too. A test that
sets a time of its own is still possible; none does after this task.

**Why not every browser test.** The other project's browser gives a
page no 3D picture (FND-059), so nothing there is drawn in software,
and the slowest of its 290 tests took 2.9 seconds in the four runs on
GitHub's Windows machine that were read. A test there that hangs is
found after 30 seconds, and that stays so.

**What it costs.** A test of the globe that hangs is now found after
90 seconds and not after 30, a minute later. The tests are not run
again when they fail (`retries: 0`), so that minute is paid once for
each test that hangs. The Windows job on GitHub has 20 minutes
(FND-057); in the planner's trial of this task on GitHub that job took
7 minutes 18 seconds, of which the 20 tests of the globe took 47
seconds together, and in the two trials of GLB-030, with seven tests
more and the whole Earth in view, 10 minutes 40 seconds and 9 minutes
11 seconds, of which the 26 tests of the globe took 131 and 130
seconds.

**The line `test.setTimeout(90_000)` goes.** With the project at 90
seconds it would say the same number a second time, and a reader
would take the test for a special case that it no longer is. Its
comment keeps the two times that were measured when the test was
written.

**How the new test holds the number.** `testInfo.timeout` is what
Playwright gives the very test that asks, after the settings of the
run, of the project and of the file have been counted;
`testInfo.config.projects` is what the settings give each project.
The first alone would pass if every test of the run had 90 seconds,
and the second says what the settings give each project by its name.
The planted defects try the settings in nine ways.

**Nothing a person sees changes**, and no test of the application is
new: this is a task of the foundation of the tests, added to Phase 3
because the globe's tests are what it is for.
