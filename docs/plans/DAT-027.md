**Phase:** 2 – Data store and published data (added on 2026-11-19 by PLAN-016)

**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §11, §12, `docs/WORKFLOW.md`, `DATABASE.md`

## Objective

One function says which migrations a store lacks, writes nothing, and
refuses exactly the stores `migrate` refuses.

## Why

The next command (DAT-025) says which schema a store has and must never
write. To say "up to date", "lacks 2 migrations", "newer than this code" or
"not a MotoSphere store", it needs what `migrate` works out before it
applies anything: is the file MotoSphere's, is its version one the code
knows, and which migrations are still to come. Today that is the first
half of `migrate`, and nothing can ask for it without migrating.

Writing the same checks a second time in the command would be two places
that must agree for ever on which store is refused. So the check becomes
one function, and `migrate` asks it. That changes code which is verified
(DAT-004, DAT-023), which is why it is a task of its own, before the
command (PLAN-016, in `PROGRESS.md`).

## Design in short

- **`pending(store, migrations=None)`** in `motosphere.db.migrations`
  returns the numbers of the migrations the store lacks, in order: a new
  store lacks all of them, a store that is up to date lacks none. It only
  reads.
- **It refuses as `migrate` did**: the two `SchemaError` sentences move
  into it unchanged, with the mark looked at before the version
  (DAT-023).
- **`migrate` asks `pending`** and applies exactly the migrations it
  names: `for number in pending(store, history)`, and the migration is
  `history[number - 1]`. The transaction, the mark and the version are as
  before, line for line.
- Like `migrate`, `pending` takes the history as an optional second
  argument, and without it reads `MIGRATIONS` at that moment.
- Nothing else changes: no sentence, no behaviour of `migrate`, no
  command. The command `migrate` (DAT-024) goes on as it is, and its
  tests pass unchanged.
- No new package.

## Acceptance criteria

1. `pending` names all migrations for a new store, those after the ones a
   store has had for a store that has had some, and none for a store that
   is up to date.
2. Asking commits nothing, and the file is byte for byte as before.
3. Without a history, `pending` asks the store's own, `MIGRATIONS`, as it
   is at that moment.
4. `migrate` applies exactly the migrations `pending` named.
5. A store `migrate` refuses (a table and no mark, the mark of another
   application, a newer store, a version below zero) is refused by
   `pending` with `SchemaError` in the same words, and is byte for byte as
   before.
6. No existing test changed, and all pass: the 24 earlier tests of
   `test_migrations.py`, the tests of the command `migrate`, and the rest.
7. The type check passes with no `ignore`, and the lint with no `noqa`.
8. The full run reports 19 of 19 gates and 886 tests (backend tests
   256).
9. On the pull request, "All gates (Linux)" and "All gates (Windows)" are
   green with those numbers, and the three jobs after the gates are
   skipped.
10. Only the files under "Scope" changed.
