# FND-054 – The browser tests do not ask Windows for random ports

**Phase:** 1 – Foundation
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** nothing that is open
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §6 and §18, `docs/WORKFLOW.md`, `TASKS.md`
("Two tracks" and the entry of this task), `PROGRESS.md` (PLAN-043 and

## Objective

The browser of the browser tests is started with the one feature turned
off that makes a connection fail by chance on Windows, and browser tests
hold it there.

## Why

Three times a run on GitHub's Windows machine failed in one browser test
that could not open the page: "page.goto: net::ERR_NO_BUFFER_SPACE at
http://127.0.0.1:4173/MotoSphere/". It was the run for `main` after
FND-019 (run 44429659797), the run for `main` after FND-053 (run
45984920265) and a trial of the planner for GLB-025 (run 45996124551).
Each time it was another test, every other test passed, the task had
changed no file the failed test reads, and the job passed when it was
run once more. The message is Windows's for "no room for one more
connection". PLAN-043 made it a task and said that the cause is to be
measured before anything is changed.

The planner measured on GitHub's Windows machine, in three runs of a
trial pull request (#178, not merged):

- **The machine has room** (run 46003052257). Windows gives out 16,384
  ports for connections made from the machine (49152 to 65535). In a
  whole run of all gates the most connections held at one moment were
  774, of which 716 were closed ones that Windows keeps for two
  minutes; about 430 were the browser's to the test server.
- **The browser picks its ports at random there.** The source of the
  browser the tests use (Chromium 153.0.8010.12, `net/base/features.cc`
  and `net/socket/tcp_socket_win.cc`) has a feature,
  `TcpPortRandomizationWin`, that is on by default for Windows 11 22H2
  and later: before every connection the browser asks Windows for a
  local port picked at random (`SO_RANDOMIZE_PORT`) instead of the next
  free one. Windows Server 2025, GitHub's machine, is such a Windows.
  Measured (run 46005653032): with the feature on, of 2,999 connections
  one after another, 0 to 2 came from the port next to the one before;
  with it off, 2,994 to 2,997.
- **With the feature on, a connection fails now and then.** Two trials,
  each in turns of a minute with the feature on and off, in one job:
  30,000 requests each way, every one on a connection of its own (run
  46005653032); and 6,000 browser contexts each way, opened and closed
  as the tests do it, with a page of five files, about 24,000
  connections each way (run 46009747401). With the feature on, 8 of
  53,978 connections failed: 2 with `net::ERR_NO_BUFFER_SPACE` and 6
  with `net::ERR_ADDRESS_IN_USE`, and one page could not be opened.
  With it off, none of 53,993 failed. The machine held about 5,000
  connections throughout, the same either way.

So the fault is in how the browser asks Windows for a port. It is not in
the application, not in the test server and not in the number of
connections the tests make. A run of the browser tests makes some
hundreds of connections; at 8 failures in 54,000 that is a failed run
now and then, which is what was seen. Why Windows refuses a port it was
asked to pick at random was not looked into: that is between the browser
and Windows.

## Design in short

A browser is told which of its features to turn off by one word it is
started with, `--disable-features=`, followed by a list of names.
Playwright already starts the browser with such a list, of 15 names. A
browser that is given the word twice does not add the two lists
together, and which of them it then takes was not relied on. So
Playwright's own word is taken out (`ignoreDefaultArgs`) and given
again with the one name added (`args`): the browser gets one list, of
16 names.

`frontend/e2e/browser.ts` writes Playwright's list out, as Playwright
1.63.0 has it, builds both words from it and exports the launch options
`TEST_BROWSER`. `frontend/playwright.config.ts` sets
`launchOptions: TEST_BROWSER` for every test.

The list has to be written out: `ignoreDefaultArgs` takes a word out
only when it is given the word exactly, and the settings cannot start a
browser to ask Playwright what it is. That makes the list a copy, and a
copy can fall behind. The third of the five tests is there for that: it
starts a browser with none of the project's options and expects the
word Playwright gives to be the one `browser.ts` has. After an upgrade
of Playwright that changes the list, that test fails until `browser.ts`
follows.

## The five tests

In `frontend/e2e/browser.spec.ts`, in `the browser of the tests`:

1. `is started with one list of features to turn off, which names the
   random ports`: a browser started as the tests start theirs was given
   the word exactly once, and it is the word of `browser.ts`.
2. `is told Playwright's own list, and after it the feature of the
   random ports`: the word is Playwright's 15 names and then
   `TcpPortRandomizationWin`, no name twice.
3. `has Playwright's own list as Playwright gives it`: see above.
4. `takes its ports in order where Windows would give it ports at
   random`: what the feature is turned off for, seen from outside. The
   test starts a server of its own, which closes every connection after
   one answer, has the page open 40 connections to it one after
   another, and reads the port the browser came from each time. All 40
   must arrive. On Windows at least 20 of them must come from a port
   that is one to four after the one before. In the measurement more
   than 99 in 100 did with the feature off, and fewer than 1 in 200
   with it on, so the test is far from both. On other systems there is
   no such feature and the system gives out ports its own way: there
   the test has the 40 connections arrive and holds nothing about their
   order. It is the test that fails, on a Windows machine, when a later
   browser knows the feature under another name or not at all.
5. `is set for the one project there is`: the settings have one
   project, and its browser is started with exactly `TEST_BROWSER`.

The first four are about a browser; the first and the third start one
more browser each (`chromium.launchServer`) to read the words it was
started with, and close it again. The fourth uses the page of the test,
which is in the browser every test runs in. Its server listens on
`127.0.0.1` only, on a port the system picks, and is closed when the
test ends, also when it fails.

## What the trial settled

- **The feature is turned off, not worked around.** Fewer connections,
  a pause between tests or connections kept open would make the fault
  rarer and leave it in.
- **On Linux and macOS nothing changes.** The feature exists on Windows
  only; a browser ignores a name it does not know in the list. All 261
  browser tests pass on Linux with the browser started this way.
- **The fourth test holds something on Windows only, and says so.** A
  test that is skipped elsewhere would be counted as skipped, and the
  full run allows none. So the test runs everywhere and what it expects
  of the order depends on the system: at least half on Windows, nothing
  elsewhere. On a developer's Windows machine it expects what it
  expects on GitHub's; it was tried on GitHub's only.
- **40 connections, at least half in order, one to four apart.** One
  apart is the rule with the feature off; something else on the machine
  can take a port in between, which is why four are allowed and only
  half are asked for. With the feature on, 20 of 40 ports within four
  of the one before do not happen by chance: the ports are picked from
  16,384.
- **The page of the fourth test reports no problem.** Every browser
  test fails when its page reports one (`fixtures.ts`). The server
  answers every request with a page that names an empty icon, so the
  browser asks for nothing that is not there.

+ * Starts one more browser and gives every list of features to turn off that

+ * options of the project unless the call says otherwise, so no options
+ * means: as the browser of every test is started.

+async function featuresOffOf(options: LaunchOptions = {}): Promise<string[]> {
+  const started = await chromium.launchServer(options)
+  try {
+    return started.process().spawnargs.filter((word) => word.startsWith(FEATURES_OFF))
+  } finally {
+    await started.close()
+  }
+}

+/** Two ports are in order when the second is at most this far after the first. */
+const NEXT_IS_WITHIN = 4
+
+/**
+ * Has the page open one connection after another to a server of the test's
+ * own, which closes each after one answer, and gives the port the browser
+ * came from each time, in the order the connections arrived.
+ */
+async function portsOf(page: Page): Promise<number[]> {
+  const ports: number[] = []
+  const server = createServer((_request, response) => {
+    response.writeHead(200, {
+      'Content-Type': 'text/html',
+      'Cache-Control': 'no-store',
+      Connection: 'close',
+    })
+    response.end('<!doctype html><title>ports</title><link rel="icon" href="data:,">')
+  })
+  server.on('connection', (socket) => {
+    ports.push(socket.remotePort ?? 0)
+  })
+  await new Promise<void>((resolve) => {
+    server.listen(0, '127.0.0.1', resolve)
+  })
+  try {
+    const address: AddressInfo | string | null = server.address()
+    if (address === null || typeof address === 'string') {
+      throw new Error('the server of the test has no port')
+    }
+    for (let visit = 0; visit < CONNECTIONS; visit += 1) {
+      await page.goto(`http://127.0.0.1:${address.port}/`)
+    }
+  } finally {
+    server.closeAllConnections()
+    await new Promise<void>((resolve) => {
+      server.close(() => {
+        resolve()
+      })
+    })
+  }
+  return ports
+}
