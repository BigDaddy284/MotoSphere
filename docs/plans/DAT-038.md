# DAT-038 – No two constraints of one name in a table

**Phase:** 2 – Data store and published data
**Depends on:** DAT-037 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §12, `docs/WORKFLOW.md`, `DATABASE.md`
("The rules every table keeps"), `TESTING.md` ("The rules every table
keeps"), `PROGRESS.md` (PLAN-022), `backend/src/motosphere/db/base.py`,
`backend/tests/unit/test_db_base.py`,
`backend/tests/integration/test_base.py`

## Objective

The test that holds every table to the rules names a table that has two
constraints of the same name.

## Why

While DAT-037 was trialled, one planted defect of an earlier task failed
one test more than it had before (PLAN-022 in `PROGRESS.md`). Under that
defect a table of the tests has two checks of one name, and
`broken_rules` looked for a column's check by its name, in the
constraints of the table, which SQLAlchemy keeps as a set. With two of
one name it went by the one it came to last, and the order of a set is
not fixed.

No model has such a table. But SQLite takes one: it keeps both checks,
and when it refuses a row it says the one name, which does not tell
which of the two refused it. Nothing said so until now. The first real
table is next (the information sources, DAT-006), and the test that
holds every table to the rules should name this before a table can have
it.

## Design in short

- **`broken_rules` gets one more rule**, the last it says of each table:
  a name that more than one constraint or index of the table has is
  named, once, with how many have it:
  `The table odd_one gives the name ck_odd_one_laps_sane to 2 of its
  constraints and indexes: each must have a name of its own.`
- **Where a table has several such names** they come by the alphabet.
- **`_without_their_check` no longer goes by an order.** It keeps, for
  each name, every text a check of that name has. A column has its check
  if one of them is the text of its own check.
- No new module, no new package, no model, no table, no migration. One
  code file changes, `base.py`, and tests are added to the two files
  that test it.

## What the task left open, and what the trial settled

- **What is counted.** Every constraint of the table but the key, which
  has no name, and every index, in one count: checks, what must be
  unique, foreign keys and indexes. These are the ones `broken_rules`
  already looks at for a name given by hand (`named`), so the two rules
  go by one list.
- **How two get one name.** The naming rule makes a name from the kind,
  the table and the columns, so two of one kind on the same columns get
  one name: a column that is unique and said so again of the table
  (`uq_odd_one_code`), a foreign key said twice, an index said with the
  column and again of the table. A check gets the last part of its name
  from the model, so two checks that a model calls the same get one
  name. A name given by hand can be given twice as well.
- **Whether the rule has to say anything of indexes.** SQLite itself
  refuses two indexes of one name: the store cannot be made. The rule
  names them all the same. It costs nothing, and the test of the models
  then says in plain words what is wrong, before anything is made. An
  integration test shows both: SQLite's refusal and the rule's sentence.
- **Once for each name, with how many.** Three checks of one name are
  one sentence that says 3, not two or three sentences.
- **Where the sentence comes.** After everything else the rule says of
  the table. A name given by hand to two constraints is named for both
  reasons: twice as given by hand, as before, and then once as given
  twice.
- **The same name in two tables is not a name given twice.** The naming
  rule puts the name of the table into every name, so only a name given
  by hand can be the same in two tables, and such a name is named as
  one already. The count is made table by table, and a test holds it
  there.
- **A column with two checks of the name of its own check.** It has its
  check if either of the two is that check. That there are two is said
  by the new rule, so nothing is lost. A test gives the two in both
  orders, with one of them the column's own check and with neither, and
  the answer is the same in both orders.
- **How a test gives a set an order.** `Table.constraints` is a set. The
  tests put a list in its place with `monkeypatch.setattr`, which the
  code reads in the same way, and so decide the order themselves. The
  test of the alphabet gives the constraints from the end of the
  alphabet first, so that it cannot pass by chance.
- **What SQLite does with two checks of one name** (3.53.1). It takes
  the table. The statement the file keeps has
  `CONSTRAINT ck_twice_checked_laps_sane CHECK` twice. Each of the two
  refuses a row, and both refusals read
  `CHECK constraint failed: ck_twice_checked_laps_sane`.
- **What SQLite does with two indexes of one name.** It makes the first
  and refuses the second: `index ix_twice_indexed_code already exists`.
