## Objective

The store itself keeps a decision on a review item: an item that was
decided is neither edited nor deleted, whoever writes to the table.

## Why

"Preserve original records and update history wherever practical."
(CLAUDE.md §11). A person's decision on a doubt is such a record: the
code that later merges two records, or gives a field another value,
goes by it, and a person is not asked again what they have answered
(DAT-050). Since DAT-052 the function `decide` refuses an item that was
decided, but a statement written past the function can still put the
item back to open, give it another decision or reason, or delete it,
and a test of DAT-010 puts that on record. What holds is what the store
refuses, as with the history (DAT-048).

## What this task is, and what it is not

- **It is** two triggers on `review_item`, in a tenth migration and in
  the model alike, and their tests.
- **It is** one test of DAT-010 turned round: the one that put on
  record that the table did not keep a decision.
- **It is not** a change to `decide`, to the functions that open an
  item, or to any column, check or index. The schema goes from
  version 9 to version 10.
- **It is not** the rule that a decided item is not replaced. A
  statement that says `REPLACE` takes out the row its new row clashes
  with and fires no trigger for it. That is a task of its own,
  DAT-055 (PLAN-037), and a test of this task puts the gap on record.

## Design in short

    CREATE TRIGGER tr_review_item_decided_never_edited BEFORE UPDATE ON review_item
    WHEN OLD.state != 'open'
    BEGIN
        SELECT RAISE(ABORT, 'A decided review item (review_item) is never edited.');
    END

    CREATE TRIGGER tr_review_item_decided_never_deleted BEFORE DELETE ON review_item
    WHEN OLD.state != 'open'
    BEGIN
        SELECT RAISE(ABORT, 'A decided review item (review_item) is never deleted.');
    END

- **In the migration** `keep_the_decision_of_a_review_item`, the tenth,
  each is written out as plain SQL, as every migration is.
- **In the model** the two statements are text in the module of
  `ReviewItem`, and a listener makes them with the connection that
  has just made the table, as the model of the history does
  (DAT-048). The test of the models and the migrations compares the
  two, the sentences letter for letter, and is unchanged.
- **The names** follow `tr_record_change_never_edited`: `tr_`, the
  table, what it holds.

## What the task left open, and what the trial settled

- **Which changes of a decided item are refused?** Every one. Not
  only the state, the person and the moment: also the note, the
  reason, the record, the source, what the source says, the key and
  the moment the item says it was last changed. The whole row is the
  record of what was decided and about what. An item whose reason or
  record could still change would come to say that a person decided
  something they never saw. So the trigger names no column, and a
  column a later task adds is held without anyone thinking of it; a
  test holds that every column of the table has its case.
- **Can the note of a decided item still change?** No. `decide` takes
  the note with the decision. Where a later remark is written is for
  the administration to say (Phase 10); to leave one column open here
  would make the rule one that has to be explained.
- **How does the trigger know a decided item?** By what the row was
  before the statement (`OLD.state != 'open'`), not by what it would
  become. So an open item is changed as before, and to decide it is
  such a change: `decide` works unchanged, and so does plain SQL. From
  the statement that decides it on, the item is kept. The check of
  the table already holds the state to one of three texts, so "not
  open" is "accepted or rejected".
- **Is a change that changes nothing refused?** Yes (`SET state =
  state`). SQLite fires the trigger for every row a statement meets,
  whatever it would hold afterwards, and a rule with an exception for
  it would need the trigger to compare all sixteen columns.
- **Can an open item be deleted?** Yes, as before. Whether a doubt
  that was opened may be taken back is not decided here, and nothing
  in the store's code deletes one.
- **Can an item be stored as decided in one statement?** Yes, as
  before. The triggers are for a row that is there.
- **What does a refusal take back?** The statement (`RAISE(ABORT)`),
  as with the history: what it had done to other rows before it met
  the decided item is taken back, what the work did before stays, and
  code that catches the refusal can go on. In a unit of work nothing
  catches it, and the unit fails as a whole. The tests hold both on a
  plain connection, so that `RAISE(FAIL)` and `RAISE(ROLLBACK)` are
  each told apart from it.
- **What is a store given that holds decided items already?** The two
  triggers and nothing else. The migration reads and changes no row;
  the items are held from then on as they are. No real store has
  items yet.
- **What of `INSERT OR REPLACE`?** It is the one way left to lose a
  decided item, and it is not closed here. To close it the store must
  ask before every new and every changed row whether it would take
  the place of a decided item, by the key and by both indexes of
  DAT-050, and some of the refusals of DAT-050 then say another
  sentence. That is more than one objective and is DAT-055. Nothing
  in the store's code says `REPLACE`.
- **Why did a test of the history change?** Its helper listed every
  trigger of the store and held them to the four of the history. The
  store has six now. The helper asks for the triggers of
  `record_change`, and the test says in its name that it is about
  that table; the new file asks the same of `review_item`.

@contextmanager
def refused(why: str) -> Iterator[None]:
    """SQLite refuses what the block writes, and says exactly this."""
    with pytest.raises(IntegrityError) as refusal:
        yield
    assert str(refusal.value.orig) == why


def everything(store: Engine) -> list[tuple[object, ...]]:
    """Every item with every column, as SQLite holds it, by the key."""
    with store.connect() as connection:
        found = connection.exec_driver_sql("SELECT * FROM review_item ORDER BY id")
        return [tuple(row) for row in found]


def states(store: Engine) -> list[tuple[object, ...]]:
    """The key of every item with its state, who decided and its note, by the key."""
    with store.connect() as connection:
        found = connection.exec_driver_sql(
            "SELECT id, state, decided_by, note FROM review_item ORDER BY id"

        return [tuple(row) for row in found]


def triggers(store: Engine) -> list[tuple[str, str]]:
    """Every trigger of the table of the review queue, by name."""

            "SELECT name, tbl_name FROM sqlite_master "
            "WHERE type = 'trigger' AND tbl_name = 'review_item' ORDER BY name"
        )
        return [(str(name), str(table)) for name, table in found]
