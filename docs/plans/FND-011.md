# FND-011 – Frontend linting and formatting

**Phase:** 1 – Foundation
**Depends on:** FND-010 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §14, `docs/WORKFLOW.md`, `ARCHITECTURE.md` §3, §9

## Objective

Make likely bugs, unsafe patterns, accessibility mistakes and code style an
automatic, mandatory gate for the frontend: `npm run lint` (oxlint) and
`npm run format:check` (Prettier).

## Tool decision (already made, do not revisit)

The linter is **oxlint**, not ESLint. Reasons, recorded in `ARCHITECTURE.md`
§3:

- The project uses TypeScript 7, the native compiler. `typescript-eslint`
  depends on the older JavaScript compiler API, so the classic ESLint set-up
  is not a safe fit.
- The current Vite React template itself ships oxlint.
- oxlint has the rules we need built in (React hooks, accessibility, import,
  Vitest, TypeScript) with no extra plugin packages: one dev dependency.

Type-aware linting is not part of this task; `npm run typecheck` already
covers type errors.

## Implementation detail

The planner trial-ran this exact set-up on the merged frontend with
oxlint 1.94.0 and prettier 3.10.1: lint passed on all 7 project files, the
format check passed after one file was reformatted, the 5 unit tests, type
check and build still passed, the bundle was unchanged, and `npm audit`
reported no vulnerabilities.

### 1. Dependencies and scripts

From `frontend/`: `npm install -D oxlint prettier`. Commit the regenerated
`package-lock.json` exactly as npm writes it.

Add to `scripts` in `frontend/package.json`, after `preview`:

```json
"lint": "oxlint --deny-warnings",
"format": "prettier --write .",
"format:check": "prettier --check ."
```

`--deny-warnings` makes a warning fail the gate, the same as an error.

### 2. `frontend/.oxlintrc.json`

Exactly this content:

```json
{
  "$schema": "./node_modules/oxlint/configuration_schema.json",
  "plugins": ["react", "typescript", "oxc", "unicorn", "import", "jsx-a11y", "vitest", "promise"],
  "categories": {
    "correctness": "error",
    "suspicious": "error"
  },
  "rules": {
    "eqeqeq": "error",
    "no-console": "error",
    "no-eval": "error",
    "import/no-unassigned-import": [
      "error",
      { "allow": ["**/*.css", "@testing-library/jest-dom/vitest"] }
    ],
    "react/exhaustive-deps": "error",
    "react/no-danger": "error",
    "react/only-export-components": ["error", { "allowConstantExport": true }],
    "react/react-in-jsx-scope": "off",
    "react/rules-of-hooks": "error",
    "typescript/ban-ts-comment": "error",
    "typescript/no-explicit-any": "error",
    "typescript/no-non-null-assertion": "error"
  },
  "ignorePatterns": ["dist", "node_modules"]
}
```

Why each non-default choice exists:

- `categories`: every "correctness" and "suspicious" rule of every listed
  plugin is an error. The lock file pins the oxlint version, so the rule set
  only changes when the dependency is deliberately upgraded.
- `no-console`: the browser console must stay clean; a later task adds a
  proper way to report problems.
- `react/no-danger` and `no-eval`: scraped text is untrusted (`CLAUDE.md`
  §14). Rendering raw HTML or evaluating strings is banned outright.
- `import/no-unassigned-import` with two allowed patterns: imports that exist
  only for their side effect are rejected, except style sheets (needed from
  FND-013) and the test matcher set-up that already exists in
  `src/test/setup.ts`.
- `react/react-in-jsx-scope` is the one rule switched off: the project uses
  the automatic JSX runtime, where importing `React` in every file is not
  needed and the rule is simply wrong.
- `react/only-export-components` allows constant exports because `App.tsx`
  exports `APP_NAME` and `APP_TAGLINE` next to the component.
- `ignorePatterns` must list `node_modules` explicitly: in the trial, oxlint
  linted installed packages when it was missing.

### 3. `frontend/.prettierrc.json`

  "singleQuote": true,

This matches the style the frontend is already written in (no semicolons,
