# GLB-024 – The engine's own files in development

**Phase:** 3 – Interactive 3D Earth
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** GLB-022 (merged), FND-052 (merged), FND-053 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §9 and §12, `docs/WORKFLOW.md`, `TASKS.md`
("Two tracks" and the entry of this task), `ARCHITECTURE.md` §3,
`TESTING.md` ("The engine's own files in the site"),
`frontend/vite.config.ts`, `frontend/sitebuild/engineFiles.ts`,
`frontend/sitebuild/engineFiles.test.ts`, `frontend/e2e/engine.spec.ts`

## Objective

In development the engine's files are answered at the same addresses as
in the built site, with the same bytes.

## Why

Since GLB-022 the built site holds the 275 files the engine of the globe
fetches while it runs, under the folder `cesium/` of the site's path. A
step of the build puts them there. `npm run dev` builds nothing: the
development server answers from the folder of the project, where the
engine's files are not. A globe that is developed with `npm run dev`
would find none of its background scripts, programs, tables and
pictures, or would be developed against something other than what the
site holds.

## What this task is, and what it is not

- **It is** a second step in `frontend/sitebuild/engineFiles.ts`,
  `engineFilesInDevelopment`, which answers the folder `cesium/` of the
  site's path from the installed engine while the development server
  runs, and its place in `frontend/vite.config.ts`.
- **It is** a table in that file, `SERVED_AS`, of what the development
  server says each of the engine's eight kinds of file is.
- **It is** 51 unit tests in a new file,
  `frontend/sitebuild/engineFilesInDevelopment.test.ts`, which start the
  development server itself and ask it over the network.
- **It is not** a change to the built site or to the step of the build:
  `engineFilesInTheSite` and everything it uses stay as they are, and
  the 16 unit tests and 23 browser tests of GLB-022 are untouched.
- **It is not** telling the engine where the files are. That is
  GLB-025. Nothing of the application asks for a file of the folder
  yet.
- **It is** one sentence of `TESTING.md` brought up to date, in the
  passage this task changes: it still said that what GitHub Pages says
  a program and a JPEG picture are "is not held yet: that is FND-053".
  FND-053 is merged, and the planner saw the sentence only afterwards.
- **It is not** a browser test. The gates' browser tests run against
  the built site (`npm run build && npm run preview`); the development
  server is started by the unit tests, which need no browser.

## Design in short

- **The same list as the build.** The step calls `engineFiles(project)`
  of GLB-022 once, when the server starts, and answers exactly those
  names: every file beneath the folder `Build` of the installed engine
  but the two logos that are left out. Nothing is listed a second time,
  so the development server and the built site cannot drift apart in
  which files they hold.
- **The folder is the step's, whole.** An address in the folder
  `cesium/` of the site's path is answered by the step and by nothing
  else: with the file when it is one of the list, and with "not found"
  (404, no content) for every other. That is what the built site
  answers. Without this, Vite would look for the address in the folder
  of the project and in `public/`, and a file put there by mistake
  would be answered in development and be missing in the site.
- **Everything else is passed on.** An address outside that folder, and
  a request that does not read (anything but GET and HEAD), go to the
  rest of the development server as before. A folder of the same name
  elsewhere in the project is none of the step's business.
- **The file is read anew for every request**, from the installed
  engine, as bytes. Nothing is kept: after `npm ci` with another
  version of an existing file the server answers the new one. A new
  file needs the server started again, as every change of the settings
  does.
- **The address is read as a browser writes it.** What follows a "?" is
  not part of the name, and "%" with two figures is read as the
  character it stands for. A name that cannot be read so is passed on,
  and the rest of the server answers it. A name that would leave the
  folder (`../`), written in any way, is never looked for on the disk:
  it is looked up in the list, and is not in it. So is a name with a
  stroke the other way, and a name in other capitals than the file
  has, on every computer.
- **What the file is, said by the step.** A browser runs a script and
  compiles a program only when the server says that this is what
  arrives. `SERVED_AS` says it for the eight kinds the engine brings:
  `text/css`, `image/jpeg`, `text/javascript`, `application/json`,
  `image/png`, `image/svg+xml`, `application/wasm` and
  `application/xml`. The length is said too.
- **A new kind stops the server.** When the installed engine brings a
  file of a kind `SERVED_AS` has no type for, the server does not start
  and names the file, as the build stops for a file that is listed as
  left out and is not there any more. A person then says what a browser
  must be told it is. A test holds the table to the kinds the installed
  engine brings: a type for each, and none for another.
- **`apply: 'serve'`.** The step is for the development server and for
  nothing else; the step of the build is for the build and for nothing
  else. Vite's server for the built site (`npm run preview`) has
  neither: it answers the files the build wrote.

## What the task left open, and what the trial settled

- **A new step or the same one?** The task said "the same step is
  taught". The trial made it a second step in the same file, with the
  same list and the same names: a step of Vite is for the build or for
  the server (`apply`), and one that is for both would have to be held
  apart again inside. GLB-022's own tests hold that its step is for the
  build only; they stay as they are.
- **Does the step answer "not found" itself, or pass the address on?**
  It answers. Passed on, the address would be looked for in the folder
  of the project and in `public/`. The trial has a test with a file in
  each of those two places: both are answered "not found".
- **What does the development server answer outside the folder for an
  address that names no file?** "Not found", and not the page: that is
  `appType: 'mpa'` of FND-052, which that task asked the development
  server by hand. Seven such addresses are tests now.
- **Does Windows differ?** The step does not; one test did, and was
  corrected. The trial ran on both machines on GitHub (below): the
  made-up projects are made and taken away again in the computer's
  folder for such files, also after a server that refused to start; a
  port that is free is given by the computer; and a name in other
  capitals than the file has is "not found" on Windows too, because
  the name is looked up in the list and not on the disk. What differs
  is that folder's name: on GitHub's Windows machine the computer
  gives it in a short form (`C:\Users\RUNNER~1\…`) and the step's
  sentence about an engine that is not installed names the long one
  (`C:\Users\runneradmin\…`). The test of that sentence first
  expected the whole path and failed there, with the step right. It
  now holds the sentence from the project's own folder on. Keep it so.
- **Watching the files.** The tests start the server with
  `watch: null`: no test changes a file the server would have to tell a
  browser about, and a watcher on the folder of the project is what
  would make such tests slow and, on some machines, fail for want of
  watchers. `npm run dev` watches as before.
- **What the server keeps for itself** (Vite's cache) goes to a folder
  made for the run, so the tests leave nothing in `frontend/`.

+/**
+ * The path an address asks for, without what follows a "?", and with what was
+ * written as "%" and two figures read as the character it stands for. An

+ */
+function pathAsked(address: string | undefined): string | undefined {
+  const path = (address ?? '').split('?', 1)[0] ?? ''
+  try {
+    return decodeURIComponent(path)
+  } catch {
+    return undefined
+  }

+/**
+ * The step of the development server that answers the engine's files. The
+ * development server builds nothing and answers from the folder of the
+ * project, where the engine's files are not. This step answers the folder of
+ * the site that holds them from the installed engine: each file the built
+ * site has, with its bytes, and "not found" for every other address in that
+ * folder, a file that is left out among them.
+ */
+export function engineFilesInDevelopment(): Plugin {
+  return {
+    name: 'motosphere:engine-files-in-development',
+    apply: 'serve',
+    configureServer(server) {
+      const project = server.config.root
+      const brought = join(project, ENGINE_PACKAGE, BROUGHT_IN)
+      const folder = `${server.config.base}${ENGINE_FOLDER}/`
+      const files = new Set(engineFiles(project))
+      for (const file of files) {
+        if (!Object.hasOwn(SERVED_AS, extname(file))) {
+          throw new EngineFilesError(`${file} is of a kind the development server has no type for.`)
+        }
+      }
+      server.middlewares.use((request, response, next) => {
+        const path = pathAsked(request.url)
+        const reads = request.method === 'GET' || request.method === 'HEAD'
+        if (path === undefined || !reads || !path.startsWith(folder)) {
+          next()
+          return
+        }
+        const file = path.slice(folder.length)
+        const kind = SERVED_AS[extname(file)]
+        if (!files.has(file) || kind === undefined) {
+          response.statusCode = 404
+          response.end()
+          return
+        }
+        const content = readFileSync(join(brought, file))
+        response.statusCode = 200
+        response.setHeader('Content-Type', kind)
+        response.setHeader('Content-Length', content.length)
+        // To a question about the file alone, the server sends no content.
+        response.end(content)
+      })
+    },
+  }
