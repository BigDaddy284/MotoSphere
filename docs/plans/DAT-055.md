## Objective

The store itself refuses a statement that would put another row in the
place of a decided review item.

## Why

Since DAT-054 a decided item is neither edited nor deleted. But a
statement that says `REPLACE` (`INSERT OR REPLACE`, `REPLACE`, `UPDATE
OR REPLACE`) takes out the row its new row clashes with, by the key or
as the same doubt, and SQLite fires no trigger for a row it takes out
in that way. A decided item can still be lost so, and a test of DAT-054
puts that on record with four statements. "Preserve original records
and update history wherever practical." (CLAUDE.md §11): what a person
decided is not to be lost to one word in a statement, whoever writes
it.

## What this task is, and what it is not

- **It is** two triggers on `review_item`, in a twelfth migration and
  in the model alike, and their tests. The test of DAT-054 that puts
  the gap on record is turned round.
- **It is not** a change to any column, check or index. In
  `motosphere.db.review` one sentence of one comment changes and no
  code. The schema goes from version 11 to version 12.
- **It is not** a rule for open items. An open item is edited, deleted
  and replaced as before.
- **It is not** a clean-up. The migration reads and changes no row.

## Design in short

    CREATE TRIGGER tr_review_item_decided_never_replaced BEFORE INSERT ON review_item
    WHEN EXISTS (
        SELECT 1 FROM review_item WHERE state != 'open' AND (
            (NEW.id >= 1 AND id = NEW.id)
            OR (record_table = NEW.record_table AND record_id = NEW.record_id
                AND other_record_id = NEW.other_record_id)
            OR (record_table = NEW.record_table AND record_id = NEW.record_id
                AND field = NEW.field AND source_id = NEW.source_id
                AND source_value = NEW.source_value)
        )
    )
    BEGIN
        SELECT RAISE(ABORT, 'A decided review item (review_item) is never replaced.');
    END

    CREATE TRIGGER tr_review_item_decided_never_replaced_by_another
    BEFORE UPDATE ON review_item
    WHEN OLD.state = 'open' AND EXISTS (
        SELECT 1 FROM review_item WHERE state != 'open' AND (
            id = NEW.id
            OR (... the same two records ...)
            OR (... the same thing said of the same field ...)
        )
    )
    BEGIN
        SELECT RAISE(ABORT, 'A decided review item (review_item) is never replaced.');
    END

- **Three ways to clash, and no other.** A row of `review_item` clashes
  with another by its key and by the two indexes of DAT-050. The
  triggers ask about all three, in the words of the indexes. A row of
  the other shape has nothing (NULL) in the column that is asked, and
  is equal to nothing, so the triggers need no word about the shape.
- **In the migration** `keep_a_decided_review_item_from_being_replaced`,
  the twelfth, each is written out as plain SQL, as every migration is.
- **In the model** the two statements are a third tuple of text in the
  module of `ReviewItem`, `_A_DECIDED_ITEM_IS_NEVER_REPLACED`, written
  out in full (the lint refuses SQL that is put together from pieces),
  and the one listener makes all six triggers with the connection that
  has just made the table. The test of the models and the migrations
  compares the two places, the sentences letter for letter, and is
  unchanged.

## What the task left open, and what the trial settled

- **How does the store ask?** Before the row is written, in a trigger
  for a new row and one for a changed row: is there a decided item
  that has this key, or is this doubt? After the row is written the
  item is gone, and nothing in the table says that it was there.
- **Can the store tell a statement that replaces from one that does
  not?** No. A trigger does not see what the statement says is to be
  done with a clash. So a new or changed row in the place of a decided
  item is refused whatever the statement says: where it would have
  replaced the item (the gap), where the index would have refused it
  anyway (a plain `INSERT` or `UPDATE`), and where the statement would
  have passed the row over and said nothing (`INSERT OR IGNORE`, `ON
  CONFLICT DO NOTHING`). The last is stricter than the rule needs. It
  is the price of asking in the file, and the documents say so.
  Nothing in the store's code says any of these: the two functions
  that open an item look for the doubt first.
- **What do the refusals of DAT-050 say where the item that is there
  was decided?** The sentence of this rule, "A decided review item
  (review_item) is never replaced.", because the trigger asks before
  SQLite looks into the index. Where the item that is there is open,
  SQLite names the index as before. Two tests of DAT-050 hold the
  sentence in each of the three states and change for that (below).
- **May an open item still be replaced?** Yes. It can be edited and
  deleted, so nothing is kept by forbidding it.
- **The key of a new row that names none.** Before the row is written
  it has no key and SQLite shows -1 (DAT-056). The first trigger asks
  about the key only from 1 on (`NEW.id >= 1 AND id = NEW.id`). A new
  row with a key below 1 is taken back by the triggers of DAT-056,
  after it was written, with whatever it took out. So a decided item
  with the key -1, which a store could be given before version 11,
  stops no new item, and is not replaced either. A test of the
  migration holds both, from a store at version 10.
- **Why does the second trigger ask of an open item only?** A decided
  item is never edited, and its own trigger says so. Without `OLD.state
  = 'open'` both triggers would want to stop an edit of a decided
  item, each with its sentence, and which of two triggers of one kind
  fires first is not something SQLite promises.
- **Why does the second trigger not name its columns (`UPDATE OF`)?**
  It would save one question for an edit that names none of the eight
  columns, and add eight names that must be kept right. An edit of an
  open item is rare, and the question is three searches (below).
- **The rows of one statement.** The triggers ask before every row. An
  item the statement itself stored as decided, or made decided, is a
  decided item for the rows after it. Tests hold both.
- **A connection that has SQLite fire the triggers of a delete for a
  replaced row** (`PRAGMA recursive_triggers`): the first trigger has
  said no before SQLite comes to that, in the same sentence. A test
  holds it with the setting off and on.
- **What does a refusal take back?** The statement, as with a kept
  decision: what it had done to other rows is taken back, what the
  work did before stays. In a unit of work the unit fails as a whole.
- **What does the question cost?** In the trial SQLite's plan for it
  was three searches, of the key and of the two indexes ("MULTI-INDEX
  OR"), and no table read whole. No test holds that: a trigger's own
  plan cannot be asked for, only that of the same question written
  out again, which would prove the copy.
- **Why did the tests of the earlier tasks change?** See below.

@contextmanager
def refused(why: str) -> Iterator[None]:
    """SQLite refuses what the block writes, and says exactly this."""
    with pytest.raises(IntegrityError) as refusal:
        yield
    assert str(refusal.value.orig) == why


def everything(store: Engine) -> list[tuple[object, ...]]:
    """Every item with every column, as SQLite holds it, by the key."""

        return [tuple(row) for row in found]


def doubts(store: Engine) -> list[tuple[object, ...]]:
    """The key of every item with its state and what it is about, by the key."""

            "source_value FROM review_item ORDER BY id"

def triggers(store: Engine) -> list[tuple[str, str]]:
    """The triggers against replacing on the table of the review queue, by name."""
    with store.connect() as connection:
        found = connection.exec_driver_sql(
            "SELECT name, tbl_name FROM sqlite_master WHERE type = 'trigger' AND "
            "tbl_name = 'review_item' AND name GLOB 'tr_review_item_decided_never_replaced*' "
            "ORDER BY name"
        )
        return [(str(name), str(table)) for name, table in found]
