# DAT-033 – A column without its check for empty text is named

**Phase:** 2 – Data store and published data
**Depends on:** DAT-030 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §11, §12, `docs/WORKFLOW.md`, `DATABASE.md`
("The rules every table keeps", "Text that must not be empty"),
`TESTING.md` ("The rules every table keeps", "Text that must not be
empty"), `backend/src/motosphere/db/base.py`,
`backend/src/motosphere/db/texts.py`,
`backend/tests/unit/test_db_base.py`,
`backend/tests/integration/test_texts.py`

## Objective

`broken_rules` names a column whose text must not be empty and whose table
does not have the check for it, and so the test that holds the real schema
to the rules fails on such a column.

## Why

`Base` gives the table of a model a check for every column whose text must
not be empty (DAT-030), when the model is defined. Two kinds of column get
none, both tried in the trial of DAT-030: one that a subclass of a model
adds to its parent's table, which is added after the parent was defined,
and one of a table made without a model. Such a column says that its text
must not be empty and stores empty text all the same, and nothing would
notice. `broken_rules` already names a table that is not strict, or is
without the key or the two times; this task makes it name such a column
too, before the first table is made (DAT-006).

This is the second half of what PLAN-017 called "DAT-030 – Text that must
not be empty" (PLAN-020, in `PROGRESS.md`).

## Design in short

- **One more rule in `broken_rules`, and one more sentence.** Every column
  of the type `NotEmptyText` must have its check: the one
  `not_empty(<the column's name>)` gives, which is
  - of the name the naming rule gives it,
    `ck_<table>_<column>_not_empty`, and
  - of the same text as `not_empty` writes, as SQLite is given it when the
    table is made.
- **The sentence** names the table and the column:
  `The table X does not refuse empty text in its column Y: it must have
  the check that not_empty gives for the column, named by the naming
  rule.` (one line in the list).
- **A check of another name does not count, and neither does one of that
  name that says something else.** The first would be refused by SQLite
  under a name nothing expects; the second is the dangerous one: a check
  that looks right by its name and lets empty text in.
- **How the check was written does not matter, only what SQLite is
  given.** The rule compares the text of a check as it is written into
  the statement that makes the table: with the numbers of the white space
  written out, and with a column named without its table. So the same
  check written with the table's own column, or as text, counts.
- **The order of a table's sentences**: not strict, the key, the times,
  the columns without their check, then the names given by hand. The
  columns of a table are named in their order in the table. Tables stay
  in the order of their names.
- **`Base` does not change.** It still gives the check when a model is
  defined; a column it cannot reach is named, and its table is given the
  check by hand: `table.append_constraint(not_empty("maker"))`.
  `DATABASE.md` says so, and a test does it with a real SQLite file.
- No new package, no model, no table, no migration.
  `motosphere.db.texts` does not change.

## What the task left open, and what the trial settled

- **Whether a check of the right name that says something else is named
  too**: yes, as above. A rule that asked for the name only would pass a
  check written by hand under that name that refuses less, and the name
  is exactly what makes it look right.
- **Whether `Base` should rather give the check to a subclass's column
  itself**: no, not in this task. The rule is needed either way, for a
  table made without a model, and naming the column loses nothing: the
  test that holds the real schema to the rules fails until the check is
  given.
- **Where the case of a subclass is tested**: in
  `backend/tests/integration/test_texts.py`, with two models of the
  tests' own and a real SQLite file, because it needs models and because
  what `DATABASE.md` says of giving the check by hand should be proven
  where SQLite refuses. The tables made without a model are in the unit
  tests, as for the other rules.

With only `base.py` changed, all 434 backend tests passed: no existing
table of a test has a column of the type `NotEmptyText` without its
check. One existing test is changed all the same, to pin where the new

- **How SQLAlchemy writes a check into a table's statement.** It compiles
  the check's expression for SQLite with the values written out
  (`literal_binds`) and with a column named without its table
  (`include_table=False`). Tried: compiled without the second, the same
  check written with the table's own column reads `trim(owner.name, …)`
  and would not be found; without the first, the numbers of the white
  space are question marks, and a check written as text would not be
  found. With both, the three ways of writing the check give the same
  text, letter for letter.
- **The name the naming rule gives** can be worked out without giving the
  check to a table: `NAMING["ck"] % {"table_name": …, "constraint_name":
  …}`. The rule must not give a check to the table it looks at.
- **A check written with a table's column gives itself to that table**
  (found in DAT-030). The helper of the tests that writes the check so
  therefore only makes it.

  parent's table**, with no more said (no column that tells the two
  apart is needed, and SQLAlchemy does not warn). The two models of the
  test say no more than that. With `__mapper_args__` on a model of the
  tests the lint asks for an annotation (RUF012) that the type check then
  refuses, so the models have none.
- **A check given to the table after the model was defined** is written
  into the table when it is made: the real SQLite file has it, by its
  name, and refuses the space that cannot be broken in the column.
- **The integration test changes the table of its two models once**, when
  it gives the check. No other test uses those two models or their

## Acceptance criteria

1. `broken_rules` gives one sentence, the one under "Design in short",
   for a column whose text must not be empty and whose table is without
   its check, in each of these ways: no check; the check under another
   name; a check of the right name that refuses only text with no
   characters, one that takes off spaces only, and one that is of another
   column. Another column's check does not count for it.
2. The column is named until its table has the check, and no longer once
   it has, in each of three ways of writing it: as `not_empty` gives it,
   with the table's own column, and as text.
3. The columns of a table are named in their order in the table; a column
   that may be without a value and one that may not are both named, and a
   column of ordinary text is not.
4. A table that breaks all five rules gets its sentences in this order:
   not strict, the key, the times, the column without its check, the
   names given by hand.
5. A column that a subclass of a model adds to its parent's table is
   named. Once the table is given the check, nothing is named, the real
   SQLite file has the check by its name, and it refuses empty text in
   the column and takes text that is not empty and no value.
6. The real schema and the models of the integration tests give an empty
   list.
7. The type check passes with no `ignore`, and the lint with no `noqa`.
8. The full run reports 19 of 19 gates and 1074 tests (backend tests
