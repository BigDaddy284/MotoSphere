## Objective

What the history said once it says for good: a row of `record_change`
is added and never edited or deleted.

## Why

"Preserve original records and update history wherever practical."
(CLAUDE.md §11). DAT-009 made the table that keeps what a record held
before it was changed, and DAT-047 the function that writes into it.
Until now nothing stops anyone from putting a row right afterwards or
from tidying old rows away, and a history that can be changed proves
nothing about what the store said. This task closes that, before the
first table of records (DAT-011) and so before the first row of
history is ever written.

## Design in short

- **The refusal stands in the store itself**, as four triggers on
  `record_change`. SQLite stops the statement that fires one and gives
  the trigger's sentence as the error:

  | Trigger | Fires | The sentence |
  |---|---|---|
  | `tr_record_change_never_edited` | before a row is edited | `A row of the history (record_change) is never edited.` |
  | `tr_record_change_never_deleted` | before a row is deleted | `A row of the history (record_change) is never deleted.` |
  | `tr_record_change_never_replaced` | before a new row whose key a row already has | `A row of the history (record_change) is never replaced.` |
  | `tr_record_change_key_positive` | after a new row whose key is below 1 | `A key of the history (record_change) is 1 or more.` |

- **The sixth migration**, `let_the_record_changes_only_be_added_to`,
  makes them, in plain SQL. The schema is at version 6.
- **The model says the same four statements**, as text in its module,
  and makes the triggers with the connection that has just made the
  table. So a store made from the models has them too, and the test of
  the models and the migrations, which compares triggers already,
  holds the two together to the letter of each sentence.
- No table, no column and no index changes. No new package. No
  refusal in the model: one place says it.

## What the task left open, and what the trial settled

- **In the model, in the store, or both?** In the store only. A
  refusal in the model holds whoever goes through the model and nobody
  else: not `update(RecordChange)`, which edits many rows in one
  statement and loads none, not plain SQL, not another program that
  opens the file. A trigger is part of the file. The trial edits and
  deletes through the model in five ways, with plain SQL, and on a
  connection made with Python's own `sqlite3`, on which the store's
  code has switched nothing on (foreign keys are off there): every one
  is refused in the same sentence. A second refusal in the model would
  say the same in other words, and the two would have to be kept
  alike.
- **REPLACE gets past a trigger for a delete.** `INSERT OR REPLACE`
  (and `REPLACE`) takes a row with the same key out and puts the new
  row in, and SQLite fires no trigger for the row it takes out unless
  a connection has asked for that (`recursive_triggers`). The trial
  tried it with the first two triggers alone: both statements put a
  new row in the place of an old one. So there is a third trigger. It
  fires before every new row and asks whether its key is taken. It
  cannot tell what the statement would have done then, so it refuses
  them all alike: a plain `INSERT` with a key that is taken, `INSERT
  OR IGNORE`, and an `INSERT … ON CONFLICT` that would have edited the
  row or done nothing. A key that is free may be named, also by a
  statement that says `OR REPLACE`.
- **Why a fourth trigger.** A new row that names no key has none yet
  when the third trigger asks. SQLite shows -1 for it then (its
  documentation calls the value undefined), and gives the row the next
  key afterwards. So a row with the key -1
  would stop every new row from then on. No row has that key unless it
  is written by hand, and the fourth trigger refuses any row whose key
  is below 1, after the row has its key. The store gives keys from 1
  up, so nothing the store's code writes is refused. The tests store a
  new row beside old ones on every machine, so a SQLite that showed
  something else there would fail them at once.
- **What an edit is.** Any `UPDATE` that meets a row: a value, the
  key, only `updated_at`, and also one that sets a column to what it
  holds already. The store does not ask what would change. An `UPDATE
  OR REPLACE` that moves one row onto the key of another is refused as
  an edit, and so is an `UPDATE OR IGNORE`.
- **A statement that meets no row is not refused.** The triggers fire
  for a row. An edit or a delete that names a key no row has changes
  nothing and raises nothing, and the same holds in a history without
  rows. Two tests put that on record.
- **`updated_at`.** Every table has the column (the rules every table
  keeps), and the base sets it when a row is stored. A row that is
  never edited never moves it. It stays in the table: taking it out
  would make `record_change` the one table that breaks the rule, for
  no gain.
- **How the models and the migrations are held together.** The test
  of DAT-026 compares everything SQLite keeps a statement for, a
  trigger included, and a test of the comparison itself already names
  a trigger that only one of the two has. What was missing is a way
  for a model to say a trigger. SQLAlchemy has no word for one, so the
  module of the model has the four statements as text and a listener
  that runs them after the table is made (`after_create`). The trial
  first gave the statements to SQLAlchemy's `DDL`, which the strict
  type check does not take without an `ignore`; a plain function with
  the connection does the same and is typed.
- **The rows that were there before.** The migration asks nothing of
  them and changes none; a test stores a row at version 5, migrates,
  and the row is as it was and is then held like any other. No real
  store has a row of history yet.
- **A refusal and the unit of work.** As with every refusal of the
  store, the unit of work it happens in is taken back as a whole. A
  test writes a new row and then edits an old one in the same unit:
  neither is kept.
- **What kind of error it is.** SQLite reports a trigger that stops a
  statement as a broken constraint, so Python raises `IntegrityError`,
  as for a check or a reference, with the sentence as its text.

## What is left as it is

- The table `record_change` itself, the fifth migration, `change`
  (which already refuses a row of the history before it writes), the
  runner of the migrations and `motosphere.db.compare`: unchanged.
- `tests/integration/test_record_change.py` and

@contextmanager
def refused(why: str) -> Iterator[None]:
    """SQLite refuses what the block writes, and says exactly this."""
    with pytest.raises(IntegrityError) as refusal:
        yield
    assert str(refusal.value.orig) == why


def everything(store: Engine) -> list[tuple[object, ...]]:
    """Every row of the table with every column, as SQLite holds it, by the key."""
    with store.connect() as connection:
        found = connection.exec_driver_sql("SELECT * FROM record_change ORDER BY id")
        return [tuple(row) for row in found]


def triggers(store: Engine) -> list[tuple[str, str]]:
    """Every trigger of the store with its table, by name."""
    with store.connect() as connection:
        found = connection.exec_driver_sql(
            "SELECT name, tbl_name FROM sqlite_master WHERE type = 'trigger' ORDER BY name"
        )
        return [(str(name), str(table)) for name, table in found]


def two_rows(store: Engine) -> None:

        connection.exec_driver_sql(A_ROW, ("length_in_metres", None, "1600"))

@pytest.mark.parametrize(
    ("statement", "given", "why"),
    [
        (EDITS[0], (), NEVER_EDITED),
        (DELETES[0], (), NEVER_DELETED),
        (ONTO_A_ROW[1], (1,), NEVER_REPLACED),
        (ONTO_A_ROW[2], (-1,), KEY_BELOW_ONE),
    ],
    ids=["an edit", "a delete", "a row in the place of a row", "a key below one"],
)
def test_the_refusal_holds_on_a_connection_the_stores_code_did_not_open(
    history: Engine, statement: str, given: tuple[int, ...], why: str
) -> None:
    # The store's code switches foreign keys on for every connection it
    # opens. The triggers are in the file, and need no one to switch them on.
    with closing(sqlite3.connect(str(history.url.database))) as bare:
        assert bare.execute("PRAGMA foreign_keys").fetchone() == (0,)

        with pytest.raises(sqlite3.IntegrityError) as refusal:
            bare.execute(statement, given)
        bare.commit()

    assert str(refusal.value) == why
    assert everything(history) == AS_IT_WAS
