# FND-043 – The loading test waits for its request

**Phase:** 1 – Foundation (a repair, added on 2026-11-19 by PLAN-015)
**Depends on:** FND-028 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, `docs/WORKFLOW.md`, `TESTING.md` (the
paragraphs on the browser tests under "Gates"),
`frontend/e2e/status.spec.ts`, `frontend/e2e/fixtures.ts`,
`frontend/src/data/useManifest.ts`, `frontend/src/data/DataStatus.tsx`

## Objective

The browser test "says the data is loading until it arrives" passes or
fails for what the page does, never for the moment at which it looks.

## Why

The builder of DAT-004 ran all the gates, and one browser test that
DAT-004 does not touch failed. The next run, with no file changed, passed:

```
[chromium] › e2e/status.spec.ts:117:3 › data status › says the data is loading until it arrives
Error: expect(received).toHaveLength(expected)
Expected length: 1
Received length: 0
```

The test (from FND-028) holds the request for the manifest back, waits
until the page says "Loading data…" and then expects, at once and without
waiting, that the request has arrived:

```ts
await expect(dataStatus(page)).toHaveText('Loading data…')
expect(held).toHaveLength(1)
```

But the page says "Loading data…" from its first drawing. It sends the
request a moment later (in an effect, after the drawing), and the request
then has to reach the test. Nearly always it is there first. Sometimes it
is not, and then the test fails although the page is right.

A test that can fail by chance is a defect. It makes a correct change look
wrong, it teaches everyone to run the gates again until they pass, and the
day it hides a real fault nobody looks. So it is repaired now, before the
store goes on.

## Design in short

- **The test waits for the request, then reads the page.** The two lines
  change places and the first one waits:
  `await expect.poll(() => held.length, …).toBe(1)`, and only then
  `toHaveText('Loading data…')`. That is also what the test's name says:
  while the request is held back, the page says that the data is loading.
- **Only the test changes.** The page is right, and nothing under
  `frontend/src` changes.
- **Exactly one request** is still what the test expects: `toBe(1)` fails
  for none and for two.
- **The rule goes into `TESTING.md`**: a check that does not wait is right
  only for what must have happened before the thing the test waited for
  last.
- No new package: `expect.poll` is part of Playwright.

## Verification

Port 4173 must be free, and never run two browser test runs at once. In
this development environment the browser is already installed: do **not**
run `npx playwright install` here. Each run of a browser test builds the
site first, so a change under `frontend/src` is in the next run without
anything else to do.

The one test is run with this command, from `frontend`:

```
npx playwright test e2e/status.spec.ts -g "says the data is loading until it arrives" --trace off --reporter=line
```

### Prove it first, in this order

Do not commit any of these changes.

1. **The fault, met every time.** Before you apply the diff: in
   `frontend/e2e/status.spec.ts`, in the test "says the data is loading

   `const held: (() => Promise<void>)[] = []`:

