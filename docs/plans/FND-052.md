**Phase:** 1 – Foundation

## Objective

The server the browser tests run against answers an address that names
no file with "not found" (404), as GitHub Pages does, and not with the
page.

## Why

The published site is files on GitHub Pages. An address that names no
file is answered there with the status 404. The server of the build
under test (`vite preview`) and the development server (`vite`) answer
such an address with the page itself and the status 200: Vite takes the
site for an application that reads the address itself, and hands every
unknown address to it. MotoSphere does not read the path of the
address (ARCHITECTURE.md §3: what can be shared lives after the "?" or
the "#").

So a browser test that asks the site under test for a file the build
left out is given an answer, a page of HTML with the status 200. The
file would be missing on the published site only, where no browser
test runs. The planner found it while trying GLB-022, which puts 276
files of the globe engine into the site and whose tests ask whether
files are there or not: a test that a file was left out could not
fail. A gate that cannot see a missing file is a defect of the
foundation (CLAUDE.md §18: "A successful build is not proof of correct
behaviour."), so it is put right before the first task that needs it.

## What this task is, and what it is not

- **It is** one setting in `frontend/vite.config.ts`, `appType: 'mpa'`,
  with a comment that says why. Vite then answers 404 where an address
  names no file, in the preview and in development alike.
- **It is** thirteen new browser tests in `frontend/e2e/site.spec.ts`.
- **It is not** a change to the application, to the build's output or
  to anything the site publishes: the built files are the same, byte
  for byte.
- **It is not** a page of the site's own for "not found". GitHub Pages
  shows its own; a page of MotoSphere's for it would be a task of its
  own, and nothing in the application links to an address that is not
  there.
- **It is not** a test of the development server. The planner asked it
  by hand (below). A test that starts it comes with the task that
  first makes it serve something of its own (the engine's files).

## Design in short

- Vite knows three kinds of site (`appType`): `'spa'`, the default,
  answers every address that names no file with the page; `'mpa'`
  serves the pages that are there (here one, `index.html`) and answers
  404 for the rest; `'custom'` serves no page at all. This site is the
  second kind.
- The page is still answered at the site's path (`/MotoSphere/`), at
  `/MotoSphere/index.html`, and at the path with a question or a
  fragment after it, which is where the application will keep what
  can be shared.
- Nothing else in the configuration changes, and no package is added.

## What the task left open, and what the trial settled

- **Does any existing test need the old answer?** No. All 217 browser
  tests of before pass unchanged with the setting; the tests that
  need a manifest the server does not have replace the answer
  themselves.
- **Does the development server still serve the application?** Yes.
  Asked by hand in the trial (`npx vite`, Linux): the site's path,
  `index.html`, the path with a question after it, `src/main.tsx`,
  `data/manifest.json` and `favicon.svg` are answered 200 with their
  types; seven addresses that name no file are answered 404. Without
  the setting the same server answers them 200 with the page.
- **What is still not as on GitHub Pages?** The server of the build
  under test answers a file's address with a slash after it
  (`favicon.svg/`) with the file, and GitHub Pages does not; and it
  answers `/MotoSphere` without the slash with 404, where GitHub Pages
  sends the browser on to `/MotoSphere/`. Nothing asks for either.
  `TESTING.md` says that the test server is not GitHub Pages and that
  the check of the published site is what asks GitHub Pages itself.
