# DAT-063 – A command is given the store only when it is ready

**Phase:** 2 – Data store and published data
**Track:** A (see `TASKS.md`, "Two tracks")
**Depends on:** DAT-021 (`open_store`), DAT-024 and DAT-025 (the
commands `migrate` and `schema`), DAT-027 (`pending`) (all merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §8 and §12, `docs/WORKFLOW.md`,
`TASKS.md` ("Two tracks" and the entry of this task), `PROGRESS.md`
(PLAN-052), `DATABASE.md` ("The command that only looks" and the

`backend/src/motosphere/cli/migrate.py`,

## Objective

One function gives a command the data store the settings name, and only
when the store is there and at the newest schema. It makes no file and
gives the store no migration, and it says in one sentence what is
wrong.

## Why

The pipeline has two commands that use the store, and both are about
the store itself: `migrate` makes it and brings it to the newest
schema, and `schema` looks. The next command, which loads the countries
(DAT-061), is the first that works on what is in the store, and many
follow it. Each of them needs the same thing first: the store, as it
is, at the schema the code was written for.

`open_store` alone does not give that. It makes the file where there is
none, so a command that only meant to load something would leave an
empty file behind that is no store yet; and it gives a store that lacks
migrations, on which the work would fail in the middle with an error of
SQLite's. Nor is it right for such a command to migrate the store by
itself: a command that was asked for one thing would then do another as
well, to a file a person may have wanted to keep as it is.

So the question "is the store ready to be worked on" is answered in one
place, in the words the two commands already have for it, before the
first command that needs it is written. The planner's trial of DAT-061
showed the two as two tasks: this one has 17 tests of its own, and the
command then has only its own work to test (PLAN-052 in `PROGRESS.md`).

## What this task is, and what it is not

- **It is** one new module, `backend/src/motosphere/cli/store.py`, with
  a function, `store_to_work_on`, an error, `StoreNotReadyError`, and a
  sentence, `MIGRATE_FIRST`.
- **It is** 17 new tests in two new files.
- **It is** the documents: `DATABASE.md`, `TESTING.md`,
  `ARCHITECTURE.md` and `CHANGELOG.md`.
- **It is not** a command. Nothing calls the function yet; the first to
  do so is the command of DAT-061.
- **It is not** a change to `migrate`, to `schema`, to `open_store` or
  to `pending`. The function is built from them, and they stay as they
  are.
- **It is not** a change to a model or a migration. The schema stays at
  version 15.

## Design in short

The function is `store_to_work_on(settings: Settings) -> Engine`.

| The store the settings name | What the function does |
|---|---|
| There is no file | Raises `StoreNotReadyError`: "There is no data store: … does not exist. Run `python -m motosphere migrate` first." It makes no file and no folder. |
| It lacks migrations | Raises `StoreNotReadyError`: "The data store lacks 2 migrations: … is at schema version 13, and the newest is version 15. Run `python -m motosphere migrate` first." The store is not given them. |
| `migrate` would refuse it, or it cannot be opened | Raises `StoreNotReadyError` with what `migrate` says of it, word for word, and no advice: `migrate` does not put that right. |
| It is at the newest schema | Gives its engine, as `open_store` made it. |

The first part of the first two sentences is what the command `schema`
says of such a store, made by the same function
(`motosphere.cli.schema.report`). The path is the whole path of the
file, taken from the current folder, as in the two commands.

## What the trial settled

- **It takes the settings, as a command has them.** Every command is
  handed the settings (`run(arguments, settings)`), and the place of
  the store is one of them. So a command writes
  `store = store_to_work_on(settings)` and nothing else.
- **It raises, and the command decides what follows.** The error is one
  plain sentence for the user, like `StoreError` and `SchemaError`. A
  command writes it to standard error and ends with the exit code 1, as
  `migrate` and `schema` do with theirs; that is the command's part and
  is tested with the command (DAT-061).
- **The words of `schema` and of `migrate` are used, not new ones.**
  What `schema` says of a store that is not there or lacks migrations
  comes from `report` in `motosphere.cli.schema`, and what `migrate`
  says of a store it refuses comes from `open_store` and `pending`. The
  function adds one thing: where `migrate` puts the matter right, it
  says so. A test holds the refusals to what the real `migrate` command
  then says, so the two cannot come to differ.
- **The advice is written out, and a test holds it to the command
  line's own name.** `motosphere.cli.app` has the name of the program
  (`PROGRAM`), and it imports every command; a module the commands
  import cannot import it back. So `MIGRATE_FIRST` has the words
  written out, and a unit test holds them to `PROGRAM`.
- **No advice where `migrate` would not help.** A file of another
  program, a store newer than the code and a file that is no database
  are not put right by `migrate`: it refuses them too. Telling a person
  to run it would send them in a circle.
- **Nothing is written, and no connection is left open.** Every test of
  a refusal compares the file byte for byte, and looks for anything new
  beside it. Two tests ask SQLite for the file for themselves alone and
  then remove it, once after a refusal and once after the store was
  given: a connection that had read the store and was left open would
  still hold it. SQLite then gives the file to no other connection for
  itself alone, on every system, and Windows does not remove such a
  file.
- **Where it lives.** In the command line's package,
  `motosphere.cli.store`: it speaks to a person at the command line,
  in the words of two commands, and names a command. `motosphere.db`
  stays free of the command line.
- **The module name `store` is in two packages.** `motosphere.db.store`
  opens a store; `motosphere.cli.store` gives a command its store. The
  imports are absolute throughout the project, so the two cannot be
  mistaken for each other.

+"""The data store as a command that works on it is given it.
+
+``migrate`` makes the store and brings it to the newest schema, and
+``schema`` says which schema it has. Every other command that reads or
+writes the store works on it as it is, and :func:`store_to_work_on` is
+where such a command gets it: the store the settings name, and only when
+it is there and at the newest schema.
+
+Nothing is put right here. Where there is no file, none is made, and a
+store that lacks migrations is not given them: that stays with
+``migrate``, so that a command that was asked for one thing does not do
+another as well. What is wrong is said in one sentence, and where
+``migrate`` puts it right, the sentence says so.
+"""
+
+from typing import Final
+
+from sqlalchemy import Engine
+
+from motosphere.cli.schema import report
+from motosphere.core.settings import Settings
+from motosphere.db.migrations import SchemaError, pending, schema_version
+from motosphere.db.store import StoreError, open_store
+
+__all__ = ["MIGRATE_FIRST", "StoreNotReadyError", "store_to_work_on"]
+
+# What a person does about a store that is not there or lacks migrations.
+MIGRATE_FIRST: Final = "Run `python -m motosphere migrate` first."
+
+
+class StoreNotReadyError(Exception):
+    """The store cannot be worked on as it is. The message is one plain sentence for the user."""
+
+
+def store_to_work_on(settings: Settings) -> Engine:
+    """Give the store the settings name, when it is there and at the newest schema.
+
+    The store is opened the way every store is opened
+    (:func:`motosphere.db.store.open_store`), and no connection to it is
+    left open.
+
+    Raises :class:`StoreNotReadyError` when there is no file, when the
+    store lacks migrations, and when ``migrate`` would refuse the store
+    or it cannot be opened: then in the words ``migrate`` has for it.
+    Nothing is written either way, and no file is made.
+    """
+    path = settings.store_path.resolve()
+    if not path.exists():
+        # open_store would make the file.
+        raise StoreNotReadyError(f"{report(str(path), None, 0)} {MIGRATE_FIRST}")
+    try:
+        store = open_store(path)
+        lacking = pending(store)
+    except (StoreError, SchemaError) as error:
+        raise StoreNotReadyError(str(error)) from error
+    if lacking:
+        said = report(str(path), schema_version(store), len(lacking))
+        raise StoreNotReadyError(f"{said} {MIGRATE_FIRST}")
+    return store

## Acceptance criteria

1. `motosphere.cli.store` has `store_to_work_on`, `StoreNotReadyError`
   and `MIGRATE_FIRST`.
2. Where the settings name no file, `store_to_work_on` raises
   `StoreNotReadyError` with "There is no data store: … does not
   exist. Run `python -m motosphere migrate` first.", and neither the
   file nor its folder is made.
3. A store that lacks migrations is not given: the error says how many
   it lacks, its version and the newest, in the words of `schema`, and
   then the same advice. The store is not given the migrations.
4. A store `migrate` would refuse, a file that is no database and a
   folder in the store's place are refused with what `migrate` says of
   them, word for word, in one line and with no advice.
5. A store at the newest schema is given, opened as `open_store` opens
   it, and work on it is kept.
6. A relative path of the store is taken from the current folder.
7. After a refusal the file is byte for byte as it was and nothing is
   made beside it. No connection to the store is left open, refused or
   given.
8. `MIGRATE_FIRST` names the command with the command line's own name
   for the program.
9. No command, model, migration or existing test changed.
10. The four documents say what the function gives, what it refuses and
    in which words.
11. `python scripts/check.py` reports 19 of 19 gates, with 2552
    backend tests, and 17 tests more in all than `main` gives at the
    commit the branch starts from (3520 when that is `297d95d`).
12. On the pull request both gates jobs are green (Linux and Windows)
    at the first attempt, and the three jobs after the gates are
    skipped.
13. Only the seven files under "Scope" changed.
