# FND-053 – The check of the published site knows the engine's kinds of file

**Phase:** 1 – Foundation
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** GLB-022 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3 and §18, `docs/WORKFLOW.md`, `TASKS.md`
("Two tracks" and the entry of this task), `TESTING.md` ("Deployment",
from "That GitHub accepted a deployment" on), `scripts/live.py`,
`tests/scripts/test_live.py`, `frontend/e2e/site.spec.ts`,
`frontend/e2e/engine.spec.ts`

## Objective

The check of the published site has a rule for every kind of file the
site is made of, the four the engine of the globe brought among them,
and a site that gains a kind of file does not pass the gates without
one.

## Why

After every deployment `scripts/live.py` fetches each published file
and compares it byte for byte with the built one. For seven kinds of
file it also holds what the server says the file is, because that is
part of the site working: a script served as plain text is not run.

With GLB-022 the site holds 275 files of the globe engine, and with
them three kinds of file it did not have: 4 programs for the browser's
own machine (`.wasm`), 53 JPEG pictures (`.jpg`) and one XML file. A
fourth kind was there before and has no rule either: the list of the
licences, `licences.txt`. The check compares their bytes and says
nothing of their type. A browser is particular about the first: it
compiles a `.wasm` program while it arrives only when the server says
`application/wasm`. A text that is said to be anything but text is
offered for saving and not shown.

Nothing holds, either, that a kind of file has a rule at all. The
engine's kinds came into the site and every gate stayed green.

## What this task is, and what it is not

- **It is** four rules more in `scripts/live.py`, each as GitHub Pages
  was read to serve that kind.
- **It is** a list of the kinds of file the built site holds,
  `frontend/e2e/siteKinds.json`, with one browser test that holds the
  list to the site as it was built, and script tests that hold the
  check's rules to the list.
- **It is** 13 new script tests and one new browser test.
- **It is not** a change to what the check does with a file whose kind
  has no rule: it is still judged by its content alone, and the test
  of that stays as it is. No file of such a kind can reach the
  published site any more without a test failing first.
- **It is not** a change to the workflow, to the build or to anything
  the site publishes.

## Design in short

- `CONTENT_TYPES` in `scripts/live.py` gains `.wasm`
  (`application/wasm`), `.jpg` (`image/jpeg`), `.xml`
  (`application/xml` or `text/xml`, which mean the same to a browser,
  as a script has two names there already) and `.txt` (`text/plain`).
  The first name of a rule is the one the failure sentence names as
  expected.
- `frontend/e2e/siteKinds.json` is one line: the eleven kinds, each
  by the end of a file's name with its dot, in small letters, in
  order. Two languages read it, so it is JSON and not a list in
  either.
- The browser test reads `frontend/dist`, which the gates build
  before the browser tests run, takes the end of every file's name in
  small letters (as the check does), and expects exactly the list.
  It fails when the site holds a kind that is not listed, and when a
  listed kind is not in the site any more.
- The script tests expect the check's rules to be for exactly the
  listed kinds: a rule for each, and none for another. The script
  tests run before the site is built, so they cannot read the site
  themselves; the list is what joins the two.
- So a new kind of file fails the browser test until it is listed,
  and once it is listed the script tests fail until it has a rule.

  made the site under test answer, read from the real site now.
- **Do the kinds differ between the machines?** No. The list is the
  ends of the names of the files the build writes, and the browser
  test passed on Linux and on Windows in the trial on GitHub.

## Acceptance criteria

1. The check has a rule for `.wasm` (`application/wasm`), `.jpg`
   (`image/jpeg`), `.xml` (`application/xml` or `text/xml`) and `.txt`
   (`text/plain`), whatever the size of the letters of the name's end.
2. A published file of one of the four kinds that is served as
   another type fails the check with a sentence that names the file,
   the type it was served as and the type expected.

   for byte.

   site, each once, by the end of a name in small letters, in order.

   that is not listed, and when a listed kind is not in the site.
6. The script tests fail when a listed kind has no rule, and when
   there is a rule for a kind that is not listed.

   kind has no rule is still judged by its content.
