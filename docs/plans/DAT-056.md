## Objective

The store itself refuses a key below 1 for an item of the review queue,
for a new item and for one that is given another key.

## Why

The next task of this track, DAT-055, keeps a decided item from being
replaced. To do that the store asks, before every new row, whether a
decided item has the key of that row. A new row that names no key has
none until it is written, and until then SQLite shows -1 for it. A
decided item with the key -1 would so stop every new item that names no
key, which is every item the store's own code opens. The history of
changes met the same thing and holds its keys to 1 or more (DAT-048,
`tr_record_change_key_positive`). The review queue gets the same rule,
by itself and before the task that stands on it (PLAN-040; CLAUDE.md
§1: when uncertain, the smaller task).

## What this task is, and what it is not

- **It is** two triggers on `review_item`, in an eleventh migration and
  in the model alike, and their tests.
- **It is not** a change to any column, check or index, or to
  `motosphere.db.review`. The schema goes from version 10 to version
  11.
- **It is not** the rule that a decided item is not replaced. That is
  DAT-055, and the test of DAT-054 that puts that gap on record is
  unchanged and passes.
- **It is not** a clean-up. An item that has a key below 1 already is
  left as it is. No real store has items yet, and the store itself
  never gave such a key.

## Design in short

    CREATE TRIGGER tr_review_item_key_positive AFTER INSERT ON review_item
    WHEN NEW.id < 1
    BEGIN
        SELECT RAISE(ABORT, 'A key of the review queue (review_item) is 1 or more.');
    END

    CREATE TRIGGER tr_review_item_key_stays_positive AFTER UPDATE OF id ON review_item
    WHEN NEW.id < 1
    BEGIN
        SELECT RAISE(ABORT, 'A key of the review queue (review_item) is 1 or more.');
    END

- **In the migration** `hold_the_key_of_a_review_item_to_1_or_more`,
  the eleventh, each is written out as plain SQL, as every migration
  is.
- **In the model** the two statements are a second tuple of text in
  the module of `ReviewItem`, `_A_KEY_IS_1_OR_MORE`, and the one
  listener, now `_make_its_triggers`, makes the two of a kept decision
  and these two with the connection that has just made the table. The
  test of the models and the migrations compares the two places, the
  sentences letter for letter, and is unchanged.
- **The names** follow `tr_record_change_key_positive`.

## What the task left open, and what the trial settled

- **Before or after the row is written?** After. Before it, a new item
  that names no key shows -1, and a trigger that asked then would
  refuse every such item (tried: every test that opens an item fails).
  After it, the item has the key the store gave it. SQLite takes the
  row back with the statement.
- **Is 0 a key?** No. The store gives keys from 1 up; 0 is refused
  with the rest.
- **Can an open item be given another key at all?** Yes, as before,
  when it is 1 or more. Nothing in the store's code changes a key, and
  to forbid it is not needed here.
- **Why `UPDATE OF id`?** So that the second trigger fires only for a
  statement that names the key. An item that has a key below 1 from
  before the migration can then still be given a note, be decided,
  and be given a key of 1 or more; a trigger on every edit would shut
  such an item in.
- **What does the store say of a decided item that is given a key
  below 1?** "A decided review item (review_item) is never edited."
  The triggers of a kept decision ask before the row is changed,
  these after it, and SQLite fires those that ask before first. A
  test holds the order.
- **What of `INSERT OR REPLACE` and `OR IGNORE` with a key below 1?**
  Refused the same. `OR IGNORE` passes over a clash with a check or an
  index, not a trigger's `RAISE(ABORT)`.
- **What does a refusal take back?** The statement, as with a kept
  decision: what it had done to other rows is taken back, what the
  work did before stays. The tests hold both on a plain connection.
- **What is a store given that holds an item with a key below 1?** The
  two triggers and nothing else. The migration reads and changes no
  row. A test tries the migration alone on a store at version 10 with
  such an item: it is as it was, and can still be changed and given a
  key of 1 or more.
- **Why did a test of DAT-054 change?** Its helper listed every
  trigger of `review_item` and held them to the two of a kept
  decision. The table has four now. The helper asks for the triggers
  whose names begin `tr_review_item_decided_`, and the test says in
  its name that it is about those two. The new file has the one test
  that names all four "and no other".

@contextmanager
def refused(why: str) -> Iterator[None]:
    """SQLite refuses what the block writes, and says exactly this."""
    with pytest.raises(IntegrityError) as refusal:
        yield
    assert str(refusal.value.orig) == why


def everything(store: Engine) -> list[tuple[object, ...]]:
    """Every item with every column, as SQLite holds it, by the key."""
    with store.connect() as connection:
        found = connection.exec_driver_sql("SELECT * FROM review_item ORDER BY id")
        return [tuple(row) for row in found]


def keys(store: Engine) -> list[tuple[object, ...]]:
    """The key of every item with its state and its first record, by the key."""
    with store.connect() as connection:
        found = connection.exec_driver_sql(
            "SELECT id, state, record_id FROM review_item ORDER BY id"
        )
        return [tuple(row) for row in found]


def triggers(store: Engine) -> list[tuple[str, str]]:
    """Every trigger of the table of the review queue, by name."""
    with store.connect() as connection:
        found = connection.exec_driver_sql(
            "SELECT name, tbl_name FROM sqlite_master "
            "WHERE type = 'trigger' AND tbl_name = 'review_item' ORDER BY name"
        )
        return [(str(name), str(table)) for name, table in found]
