# FND-057 – The checks on GitHub's Windows machine do not run out of time

**Phase:** 1 – Foundation
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** nothing that is open
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3, §6 and §18, `docs/WORKFLOW.md`, `TASKS.md`

## Objective

The step that runs every gate on GitHub keeps its temporary files in the
runner's own folder for them, which on the Windows machine is on the work
disk, so that the Windows job ends well within its 20 minutes again.

## Why

On 2026-11-27 the job "All gates (Windows)" was cut off at its limit of
20 minutes four times, with no test failed: in the run for `main` at
`3da560f` (run 46011384280), twice in a trial of the planner (run
46013480988, both attempts), and in the run for `main` after DAT-012 was
merged (run 46016966535, for `307f1ac`). Each time the job was in the
middle of the tests of the pipeline. Because the Windows job did not end,
the three jobs after the gates did not run: the site was not published
again, and DAT-012 could not be recorded as verified.

On GitHub's Linux machine the tests of the pipeline took between 28 s and

minutes 51 seconds: four and nine seconds from being cut off.

The planner measured the cause on that machine (trial pull request #181,
run 46020195509, not merged). The tests make their files in the system's
folder for temporary files, and each test of the pipeline that needs a
store makes a real one there, in a file, and gives it every migration.
On GitHub's Windows machine that folder is
`C:\Users\RUNNER~1\AppData\Local\Temp`, on the system disk. The checkout
(`D:\a\MotoSphere\MotoSphere`) and the runner's own folder for temporary
files (`D:\a\_temp`) are on the work disk. Both ways in one job:

| | System disk (`C:`) | Work disk (`D:`) |
|---|---|---|
| A file written and removed | 0.39 ms | 0.16 ms |
| One saved change to a store | 19.40 ms | 1.01 ms |
| A store made and given every migration | 385.8 ms | 33.5 ms |
| The 2420 tests of the pipeline | 635.19 s | 81.99 s |

A second, shorter job of the same run gave 23.34 ms and 0.82 ms for a
saved change, 425.5 ms and 27.8 ms for a store, and 99.18 s and 8.15 s
for 360 tests of the pipeline. On the system disk single tests waited
70.84 s, 24.71 s and 20.32 s for their store.

So it is not the tests and not the application: it is where the machine
keeps temporary files. Each new test of the pipeline that needs a store
costs about a third of a second there, the tests grew from 1861 to 2420
in a day, and the job came to its limit.

What it is not, as measured in the same run: the machine's virus scanner
does not watch files as they are written (`RealTimeProtectionEnabled :
False`, and both disks are on its list of exceptions); and the machine
has 4 processors, as before.

## What this task is, and what it is not

- **It is** three lines in the workflow: the step "Run every gate" is
  given `TEMP` and `TMP`, the two names Windows has for the folder of
  temporary files, both set to the runner's own folder (`runner.temp`).
- **It is** two new repository checks that hold the workflow to it, one
  more expression on the short list of those a workflow may contain, a
  paragraph in `TESTING.md` and a line in `CHANGELOG.md`.
- **It is not** a longer time limit. The limit stays at 20 minutes: with
  the files on the work disk the job has room again, and a limit that
  grows with the fault would hide the next one.
- **It is not** a change to any test of the pipeline, to its `store`
  fixture or to `scripts/check.py`. No test is skipped, split off or run
  on one machine only, and a store in a test is a real file as before.
- **It is not** a change for a developer's machine: there the tests keep
  their files where the system says.

## Design in short

```yaml
      - name: Run every gate
        env:
          TEMP: ${{ runner.temp }}
          TMP: ${{ runner.temp }}
        run: python scripts/check.py
```

`runner.temp` is the folder GitHub gives each job for temporary files.
It is emptied when the job begins and when it ends. On the Windows
machine it is `D:\a\_temp`.

Python asks `TMPDIR`, then `TEMP`, then `TMP` for the folder of
temporary files, and pytest makes the folders of the tests beneath what
Python says. Node.js on Windows asks `TEMP`, then `TMP`. Windows itself
sets both, to the same folder, so both are set here: a program may read
either. `TMPDIR` is not a name of Windows and is left alone.

The step is the same on both machines, as every step of the job is. On
Linux, Python and Node.js look at `TMPDIR` first and at these two names
when it is not set; it makes no difference there which folder it is.

Only that one step is told. The steps before it install tools, and the
jobs after the gates run on Linux.

The workflow may contain expressions from a short list only
(`KNOWN_EXPRESSIONS` in `tests/repo/test_ci_workflow.py`), so that no
text from outside reaches a command. `runner.temp` is added to it: it is
a folder of the machine, not text from outside, and it does not reach a
command but the environment of one.

## The two new checks

1. `test_the_gates_keep_their_temporary_files_in_the_runners_own_folder`:
   the gates job has the step "Run every gate" exactly as above, the
   names set to `runner.temp` are `TEMP` and `TMP` and no other, there
   is one `env:` in the whole workflow, and `runner.temp` stands in it
   twice.
2. `test_python_keeps_its_temporary_files_where_each_of_those_names_says`:
   for each of the two names by itself, a Python started anew, with that
   name set to a new folder and the other two names (`TEMP` or `TMP`,
   and `TMPDIR`) taken away, says that its folder for temporary files is
   that folder. It is asked on the machine the checks run on, so on
   GitHub it is asked on Windows too.
