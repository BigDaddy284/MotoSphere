## Objective

The store itself refuses a region whose code begins with the two
letters of another country, so that the code of a region can be
trusted to say which country it is in.

## Why

A code of ISO 3166-2 begins with the code of two letters of the
country: `NZ-CAN` is Canterbury in New Zealand, whose code is `NZ`.
Since DAT-064 a region can say its code, and the table holds the form
of a code only: it would take `AT-1` for a region of New Zealand. Such
a region says two things of where it is, and whoever reads the store
could not tell which is true. The project's rule is that accuracy
comes before quantity (`CLAUDE.md` §11), so the store refuses it. The
letters of a country are a column of another table,
`country.alpha_2`, which a check of `region` cannot read; that is why
the rule was cut out of DAT-064 as a task of its own.

## What this task is, and what it is not

- **It is** four triggers, two on `region` and two on `country`, in
  the model `Region` and by a nineteenth migration; their tests; and
  the documents.
- **It is not** a change to a table, a column, an index or a row. The
  migration makes the triggers and reads and changes nothing.
- **It is not** a rule that a region has a code. A region without a
  code is asked nothing and is a part of any country, as before.
- **It is not** the standard's list: the store still does not know
  which codes there are, only that the two letters are those of the
  region's country.
- **It is not** a change to a command, or to the code that stores and
  changes records: `change` gives a region a code of its country with
  its history as before, and a wrong one is refused by the store
  itself, with the region and the history left as they were.
- **It is not** two regions of a country that share a name (DAT-066)
  or a region inside a region (DAT-065).

## Design in short

Two sentences, one for each table the refused statement writes to:

    The code of a region (region) begins with the code of its country (country).
    The codes of the regions of a country (region) begin with its code (country).

The two triggers on the regions, for a new region and for one that is
changed, ask the same question of the row as it now is:

    CREATE TRIGGER tr_region_code_of_its_country AFTER INSERT ON region
    WHEN substr(NEW.iso_3166_2, 1, 2) != (SELECT alpha_2 FROM country WHERE id = NEW.country_id)
    BEGIN
        SELECT RAISE(ABORT,
            'The code of a region (region) begins with the code of its country (country).');
    END

`tr_region_code_stays_of_its_country` is the same `AFTER UPDATE ON
region`. The two on the countries, for a new country and for one that
is changed, ask whether a region of the country now disagrees:

    CREATE TRIGGER tr_country_code_of_its_regions AFTER INSERT ON country
    WHEN EXISTS (SELECT 1 FROM region WHERE country_id = NEW.id
        AND substr(iso_3166_2, 1, 2) != NEW.alpha_2)
    BEGIN
        SELECT RAISE(ABORT,
            'The codes of the regions of a country (region) begin with its code (country).');
    END

`tr_country_code_stays_of_its_regions` is the same `AFTER UPDATE ON
country`. The model holds the four as texts
(`_THE_CODE_IS_OF_THE_COUNTRY` in `region.py`) and makes them after
the table of the regions is made, as `review_item.py` does with its
own; the nineteenth migration,
`hold_the_code_of_a_region_to_its_country`, makes the same four.

## What the trial measured and settled

- **Triggers, because a check cannot read another table.** The
  letters of a country are in `country`. SQLite's checks see the row
  they are on and nothing else.
- **A region is held when it is stored, given a code and moved.** All
  three leave a row of `region` whose code and country may disagree.
  A region can be moved together with its code in one statement: the
  trigger asks after the row is written, whether the row agrees with
  its country as it now is.
- **A country is held too.** A country whose regions have codes
  cannot be given other letters, or the codes of its regions would be
  those of no country, or of another. Without the triggers on
  `country` the rule could be passed by changing the country and not
  the region.
- **A new country can have regions already.** A statement that says
  `REPLACE` (`INSERT OR REPLACE INTO country`) puts a country in the
  place of the one that had its key, and the regions of the old are
  then the regions of the new. SQLite passes it with the rule of what
  a row points to, and fires the trigger for a new row and none for
  the row it takes out. So the countries have a trigger for a new
  country too; the first tests of the trial did not find a planted
  defect that leaves it out, and tests were written for it.
- **None of the four names a column** (the finding of DAT-068). A
  trigger that fires for the change of one column is not fired by a
  statement that sets the key of a row by one of SQLite's own names
  for it, and a country that is given another key gets the regions
  that point to that key. So each trigger fires after every change of
  a row of its table. A test gives a country the key that a region
  points to, by `id` and by `rowid`, and both are held.
- **A region without a code is asked nothing.** `substr` of what is
  not there is not there, and nothing compares with it, so the
  trigger does not fire. Such a region can be moved to any country,
  and a country whose regions have no codes can be given any letters.
- **Both letters, as text.** `NZ` and `NA` are two countries, and so
  are `NZ` and `TZ`: the tests refuse a code whose first letter alone
  is its country's, and one whose second alone is.
- **What the table itself refuses, it refuses first, in its own
  words**: a code that is not of the form, a code another region has,
  letters another country has. The triggers ask after the row is
  written.
- **A refusal takes the statement back and nothing else**
  (`RAISE(ABORT)`), whatever the statement says is to happen on a
  clash (`OR REPLACE`, `OR IGNORE`, `OR FAIL`). Of several regions
  written by one statement, one wrong code stops them all. Two
  countries cannot change letters with each other while their regions
  have codes, in whatever order the statements come.
- **A region whose country is not in the store** has no letters to be
  held to, and the rule says nothing of it: the sub-query gives
  nothing. The store's own connections refuse such a region by the
  rule that a row points to a row that is there. A test stores one on
  a connection that does not ask SQLite for that rule, and holds what
  happens when a country is then given the key it points to.
- **The regions of a country are found for the rule without reading
  the whole table**, by the index SQLite keeps for the rule of the
  names (`sqlite_autoindex_region_1`); a test asks SQLite for its plan.
- **The migration puts nothing right.** A store could hold a region
  whose code begins with the letters of another country, because
  nothing refused one until version 19. Which of the two is wrong, the
  code or the country, the migration cannot know, and the project
  never invents a value. Such a region stays as it is. From then on it
  can be put right or deleted and nothing else: given a code of its
  country or none, moved to the country of its code, or deleted; its
  country can be given the letters of its code where no other region
  minds. Every other change of it is refused, and so is every other
  change of its country, until then: that follows from triggers that
  name no column, and tests hold each part on a store that was at
  version 18 when the region was stored. No real store holds a region
  yet, because nothing loads regions.
- **The migration fails where a trigger of one of the four names is
  there already**, with what it made before that taken back and the
  store left at version 18.
- **The model and the migration agree**: the test of the models and
  the migrations passes unchanged, and planted defects that change
  one of the two alone are found by it.
- **One planted defect was no defect.** A migration that also wrote
  every region back to itself before the triggers were there changed
  no value and could be found by no test. It was taken off the list
  and replaced by one that does the same once the triggers are there,
  which fails on a store that holds a region of another country, and
  is found.

+def keep(store: Engine, region: Region) -> int:
+    """Store a region in a unit of work of its own, and give its key."""
+    with unit_of_work(store) as work:
+        work.add(region)

+def write(store: Engine, statement: str, *given: object) -> None:
+    """Write one statement past the model, as plain SQL, in a transaction of its own."""
+    with store.begin() as connection:
+        connection.exec_driver_sql(statement, given)

+def regions(store: Engine) -> list[tuple[object, ...]]:
+    """Every region as SQLite holds it: its key, its country, its name and its code, by the key."""
+    with store.connect() as connection:
+        found = connection.exec_driver_sql(
+            "SELECT id, country_id, name, iso_3166_2 FROM region ORDER BY id"
+        )
+        return [tuple(row) for row in found]
+
+
+def everything(store: Engine) -> dict[str, list[tuple[object, ...]]]:
+    """Every row of the regions and of the countries with every column, each table by its key."""
+    with store.connect() as connection:
+        return {
+            table: [tuple(row) for row in connection.exec_driver_sql(asked)]
+            for table, asked in {
+                "region": "SELECT * FROM region ORDER BY id",
+                "country": "SELECT * FROM country ORDER BY id",
+            }.items()
+        }
+
+
+def countries(store: Engine) -> list[tuple[object, ...]]:
+    """Every country as SQLite holds it: its key, its two codes and its name, by the key."""
+    with store.connect() as connection:
+        found = connection.exec_driver_sql(
+            "SELECT id, alpha_2, alpha_3, name FROM country ORDER BY id"
+        )
+        return [tuple(row) for row in found]
+
+
+def history(store: Engine) -> list[tuple[object, ...]]:
+    """What the history holds: the record, the field, and what it held and holds."""
+    with store.connect() as connection:
+        found = connection.exec_driver_sql(
+            "SELECT record_table, record_id, field, old_value, new_value FROM record_change "
+            "ORDER BY id"
+        )
+        return [tuple(row) for row in found]
+

+def the_standard(store: Engine) -> list[tuple[object, ...]]:

+def test_the_rule_is_four_triggers_two_on_the_regions_and_two_on_the_countries(
+    mapped: Engine,
+) -> None:
+    with mapped.connect() as connection:
+        found = connection.exec_driver_sql(

+            "AND tbl_name IN ('region', 'country') ORDER BY name"

+    written = {str(name): " ".join(str(statement).split()) for name, _, statement in found}

+    assert "AFTER UPDATE ON country WHEN" in written["tr_country_code_stays_of_its_regions"]
+    assert "AFTER INSERT ON region WHEN" in written["tr_region_code_of_its_country"]
+    assert "AFTER UPDATE ON region WHEN" in written["tr_region_code_stays_of_its_country"]
