# FND-056 – No unit test ends with work of the page waiting

**Phase:** 1 – Foundation
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** FND-055 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3 and §18, `docs/WORKFLOW.md`, `TASKS.md`
("Two tracks" and the entry of this task), `PROGRESS.md` (PLAN-046 and
PLAN-048), `TESTING.md` ("A unit test that starts the page"),
`frontend/src/test/setup.ts`, `frontend/vitest.config.ts`

## Objective

The set-up of the unit tests lets no test end while React still has
work waiting, so that no work of the page can run after the test's
document is gone, whatever a test written later does.

## Why

A run for `main` failed on GitHub's Linux machine although every test
passed (run 46006701452): a unit test started the whole page and ended
while React still had work waiting, its file ended, the test's document
was taken away, and the work ran afterwards with "ReferenceError: window
is not defined". FND-055 put the two tests right that start the whole
page. Nothing holds a test that is written later, and GLB-002 is next
on this track: its component loads the engine a moment after it is
shown.

The task was added (PLAN-046) as "A unit test file that ends with work
of the page waiting fails": count what is waiting when a file ends, and
fail the file. The planner's trial built that, and found two things:

- **A test that does nothing wrong ends with work waiting now and
  then.** A test that waits for the page as Testing Library advises
  (`findBy…`) goes on at the moment the page shows what it waits for.
  React may then still have a piece of work in its queue. Counted over
  five whole runs of the unit tests, 1,935 ends of the 387 tests there
  are: one test ended with one piece of React's work waiting, once
  (`DataStatus > loads the published manifest when it is given no
  loader`), and never the same way when it was run again.
- **So a guard that fails such a test fails a run by chance.** That is
  the fault the task is there to remove, in another place.

What removes the fault is to let the waiting work run while the test's
document is still there. The set-up of the unit tests does that after
each test. The fault of FND-055 then cannot come back: with the set-up
of this task, the two tests as they were before FND-055 pass every
time, with no error (see "What the planner tried"). So the task has
another name than it was added with; PLAN-048 in `PROGRESS.md` says
why.

- **It is** 19 new unit tests in a new file,

- **It is** a section in `TESTING.md` and a line in `CHANGELOG.md`.
- **It is not** a change to the application: nothing under
  `frontend/src` outside `frontend/src/test` changes, and nothing of
  `src/test` is part of the site that is built.
- **It is not** a change to any existing test. The two tests of FND-055
  stay as they are: a test that starts the page inside `act` and looks

- **It is not** a second try for a failed test, and no test is skipped.

  later, or for an answer from the network, when its test ends is not
  seen (see "What the trial settled").

## Design in short

Outside `act`, React does not do its work at once. Its scheduler asks
the system to call it back a moment later, with `setImmediate`, and the
function it hands over is always the same one, named
`performWorkUntilDeadline`. The scheduler keeps the `setImmediate` it
finds when it is loaded.

`reactsWork.ts` has four things:

- `watchReactsWork(host)` puts a watch around the `setImmediate` of a
  host, which is the system, or a stand-in for it in a test. The watch
  counts a piece of work from the moment it is asked for until it
  runs, when the function handed over has React's name; everything
  else it hands on untouched, with what it was to be given, and hands
  back what the system answers. It gives back three functions:
  `waiting()`, the number of pieces asked for and not yet run;
  `settled()`, which lets the waiting work run until none is waiting,
  looking again after each turn, and fails with a sentence after 100
  turns; and `close()`, which gives the host its own `setImmediate`
  back and fails with a sentence when work is still waiting.
- `endEveryTestSettled(watch, hooks, tidy)` hands the test runner two
  things to do: after each test, `tidy()` and then `await
  watch.settled()`; when the file is over, `watch.close()`.
- `theSystem()`, which gives the system the unit tests run on as a
  host. The application's types know no `setImmediate`, so the function
  asks the system whether it has one, and fails with a sentence where
  it has none. A test hands it something else than the system to see
  that.
- `reactsWork`, the watch of the unit tests themselves, over the
  system's own `setImmediate`. It is made when the module is loaded.

`setup.ts` brings `reactsWork.ts` in first, before Testing Library,
which loads React: the watch has to be in place when React looks for
`setImmediate`. It then calls `endEveryTestSettled` with what it did
after each test before (unmount what the test showed, clear the
session) as `tidy`.

The two sentences of the watch:

- `React still has work waiting after it was let run 100 times:
  something asks it for more work without end.`
- `The test file ends with 1 of React's work still waiting: it would
  run after the test's document is gone.` (with the number that is
  waiting)

After each test nothing is waiting, so the second is never seen while
the first step is in place. It is what is left to say so if that step
is ever lost: with `await watch.settled()` taken out, the file of
FND-055's fault fails with that sentence every time (see "What the
planner tried").

## What the trial settled

- **Let finish, not fail.** See "Why". A test that leaves work waiting
  is not told so. The fault that follows from it is what is removed.
- **After each test, not at the end of the file only.** Work that is
  left by one test and runs during the next can change what the next
  test sees. After each test the document is empty and the session
  cleared before the work runs, as it would be at the next test's
  start.
- **What the test left is put away first, then React is let finish.**
  Unmounting a page can ask React for work too; that is let run as
  well.
- **100 turns.** Work can ask for more work, so the wait looks again
  after each turn. A page that asks for more work without end would
  never settle, so the wait has a limit and a sentence.
- **The watch tells React's work by the name of the function.** The
  scheduler hands over one function of its own, named
  `performWorkUntilDeadline`. A name can change with an upgrade of
  React; test 15 fails then.
- **Only `setImmediate` is watched.** It is what React's scheduler uses
  where the unit tests run (Node with jsdom). The browser tests run
  the built site in a browser and are not this task's.
- **What is not seen.** A promise the page still waits on when its
  test ends: a file it loads later (`import()`), an answer from the
  network. The watch cannot know that React will be asked for more. A
  test of such a page waits for what it expects to see, as before, and
  `TESTING.md` says so. The work the test's document has of its own
  (one piece for each style sheet, FND-055) is not React's and is not
  counted.
- **The type checks pass with no assertion.** The application's types
  know no `setImmediate`; `theSystem()` asks the system whether it has
  one and fails with a sentence where it has none. That sentence cannot
  be reached where the tests run, so `theSystem` takes what it is to
  look at, the system unless it is told otherwise, and a test hands it
  something without a `setImmediate`.
- **One planted defect passed every test at first:** the watch closed
  after each test instead of at the end of the file. Test 11 now holds
  that the watch stays in place after a test, and all were run again.

+## What a unit test leaves waiting
+
+The two tests that start the whole page end only when React has nothing
+left to do (the section above). That does not hold a test that is
+written later, and it does not have to be a test that forgets `act`: a
+test that waits for the page as Testing Library advises (`findBy…`) can
+end a moment before React has done the last of its work. Counted over
+five whole runs of the unit tests, one test of the 387 ended so once.
+If such a test is the last of its file, the work runs after the test's
+document is gone, and the run fails with "window is not defined"
+although every test passed.
+
+So the set-up of the unit tests (`frontend/src/test/setup.ts`) lets no
+test end with work of React's waiting. It does so with
+`frontend/src/test/reactsWork.ts`:
+
+- **A watch.** React asks the system to call it back when it has work
+  to do, with `setImmediate`; the function it hands over is named
+  `performWorkUntilDeadline`. Before React is loaded, the set-up puts a
+  watch around the system's `setImmediate`. The watch counts each piece
+  of React's work from the moment React asks for it until it runs, and
+  hands on everything else untouched. That is why the watch is the
+  first thing `setup.ts` brings in: React keeps the `setImmediate` it
+  finds when it is loaded.
+- **After each test** the set-up unmounts what the test showed and
+  clears the session, as before, and then lets React's waiting work
+  run until none is waiting. Work can ask for more work, so it looks
+  again after each turn, up to 100 times. After that it fails the test
+  with "React still has work waiting after it was let run 100 times:
+  something asks it for more work without end."
+- **When the file is over** it gives the system its own `setImmediate`
+  back, and fails the file if anything of React's is still waiting:
+  "The test file ends with 1 of React's work still waiting: it would
+  run after the test's document is gone." After the step above nothing
+  is; this is what is left to say so if that step is ever lost.
+
+**Why the test is not failed instead.** The task was first to fail
+every test file that ends with work waiting. The trial showed that a
+test which does nothing wrong ends that way now and then, by a few
+moments. A guard that fails such a test fails a run now and then,
+which is the fault it was to remove. Letting the work run, while the
+test's document is still there, removes the fault itself.
+
+**What it does not see.** Only what React asks the system for is
+counted. A page that waits for something else when its test ends, a
+file it loads later or an answer from the network, is not seen: the
+watch cannot know that React will be asked for more. A test of such a
+page waits for what it expects to see, as before. Nor is the work the
+test's document has of its own counted (the section above).

+ * React does not show a page at once when it is asked to. Outside `act` it

+ * and then (FND-055).

+ * This watches what React asks for. The set-up of the unit tests lets no
+ * test end before React has nothing waiting (FND-056; TESTING.md).
+ */

+/** The function React's scheduler asks the system to call when it has work. */
+export const REACTS_WORK = 'performWorkUntilDeadline'
+
+/** How many times `settled` lets the waiting work run before it gives up. */
+export const TURNS = 100

+/** What `close` fails with when a test file ends with React's work waiting. */

+export type Work = (...given: unknown[]) => void

+/** Who gives out `setImmediate`: the system, or a stand-in for it in a test. */

+export type ReactsWork = {
+  /** How many pieces of React's work were asked for and have not run yet. */
+  waiting: () => number
+  /**
+   * Lets the waiting work run until none is waiting. Fails with
+   * `STILL_WAITING` when some is still waiting after `TURNS` turns.
+   */
+  settled: () => Promise<void>
+  /**
+   * For the end of a test file: gives the host its own `setImmediate` back,
+   * and fails with `leftWaiting` when React's work is still waiting then.
+   */
+  close: () => void
+}
+
+/**
+ * Puts a counting `setImmediate` in the place of the host's own. It must be
+ * called before React is loaded: React keeps the `setImmediate` it finds
+ * when it is loaded.
+ */
+export function watchReactsWork(host: Host): ReactsWork {
+  const real = host.setImmediate
+  let waiting = 0
+  const watched = Object.assign((work: Work, ...given: unknown[]) => {
+    if (work.name !== REACTS_WORK) {
+      return real(work, ...given)
+    }
+    waiting += 1
+    return real(() => {
+      waiting -= 1
+      work(...given)
+    })
+  }, real)
+  host.setImmediate = watched
+  const stillWaiting = () => waiting
+  return {
+    waiting: stillWaiting,
+    settled: async () => {
+      for (let turn = 0; stillWaiting() > 0; turn += 1) {
+        if (turn === TURNS) {
+          throw new Error(STILL_WAITING)
+        }
+        // What was asked for before this runs before it: one turn lets
+        // every piece that is waiting now run.
+        await new Promise<void>((resolve) => {
+          real(() => {
+            resolve()
+          })
+        })
+      }
+    },
+    close: () => {
+      host.setImmediate = real
+      if (waiting > 0) {
+        throw new Error(leftWaiting(waiting))
+      }
+    },
+  }
