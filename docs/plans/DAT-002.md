## Objective

The pipeline knows where its data store's file is from one validated
setting, and a store's file can never be committed by accident.

## Why

DAT-001 decided what the store is: one SQLite file. Before anything can
open it (DAT-021), the pipeline must know where the file is, and Git must
ignore it wherever it is: the file is rebuilt from text for every run
(`DATABASE.md`), so a committed copy would be a second, stale store.

This task was the first third of "DAT-002 – Store settings and connection
module". The planner's trial showed three things in that task that can
each be built and tested alone, so it is three tasks now (PLAN-013): this
setting, opening the store (DAT-021) and units of work (DAT-022).

## Design in short

- One new setting, `store_path`, in the settings the pipeline already has
  (`MOTOSPHERE_STORE_PATH` in the environment or in `backend/.env`). It is
  a path. The default is `store/motosphere.sqlite3`, and a relative path
  starts in the `backend` folder, where every pipeline command runs.
- **An empty path is refused when the settings are read**, in plain words.
  Without the check an empty value would quietly mean "the current
  folder". Spaces around the value are dropped, as for the other settings;
  spaces inside it stay.
- **Reading the settings creates nothing**: no file, no folder. The file
  appears when the store is first opened (DAT-021).
- **Git ignores the store**: the folder `backend/store/`, and every
  `*.sqlite3` file with the files SQLite keeps beside one
  (`*.sqlite3-journal` and the like), wherever they are. A repository
  check reads the default from `backend/.env.example` and fails if Git
  would not ignore it, so the default cannot move to a place that is not
  ignored. An existing backend test already holds `.env.example` to the
  default in the code.
- **The README's table of settings is now held to the code** by a test:
  every setting with its default, exactly once. Until now nothing compared
  the two.
- Nothing opens the store: no SQLAlchemy, no connection, no file.

Why the check has `mode="before"`: it must see the text as it was given.
Afterwards an empty text has already become the path `.`.

Why the README test writes a path with `as_posix()`: on Windows a path
prints with backslashes, and the README has one spelling.

## Acceptance criteria

1. `Settings().store_path` is the path `store/motosphere.sqlite3` when
   nothing is set, and the value of `MOTOSPHERE_STORE_PATH` from the
   environment or from `backend/.env` when it is.
2. An empty value, or one of spaces only, is refused when the settings are
   read, with a message that names `store_path` and says the path must not
   be empty. Spaces around a value are dropped; spaces inside it stay.
3. Reading the settings creates no file and no folder, with the default
   and with a set value.
4. `backend/.env.example` and the README's table list the setting with its
   default, and tests fail when either differs from the code.
5. Git ignores `backend/store/` and everything in it, every `*.sqlite3`
   file and every `*.sqlite3-*` file, anywhere in the repository; a
   repository check fails if the default in `backend/.env.example` is a
   place Git does not ignore.
6. The full run reports 19 of 19 gates and 791 tests (repository
   checks 41, backend tests 161).
7. On the pull request, "All gates (Linux)" and "All gates (Windows)" are
   green with those numbers, and the three jobs after the gates are
   skipped.
8. Only the files under "Scope" changed.
