## Objective

Where the browser gives a 3D picture, the globe stage shows the Earth,
drawn by the real engine with the pictures that come with it, loaded
only from the site itself and after the page is there.

## Why

This is the task in which the application gets its globe. Everything
for it is in place: the engine's files are in the site (GLB-022,
GLB-024) and the engine is told where (GLB-025); the stage knows
whether the browser can draw (GLB-026); the `Globe` component loads,
starts and stops an engine it is handed (GLB-027) and passes on that
the first complete picture is drawn (GLB-029). What is missing is the
real way to start the engine, and the stage showing the component with
it.

## What this task is, and what it is not

- **It is** one new module that starts the real engine
  (`frontend/src/globe/earth.ts`), the stage showing the `Globe`
  component with it and marking the globe as busy until the Earth is
  drawn, the page handing the way to load that module down to the
  stage, and the unit tests and browser tests of all that.
- **It is not** a check of the picture itself: that what is drawn is
  the Earth, the right way up and in the right place, is read from the
  pixels in GLB-003. Here the tests hold that a picture is drawn on one
  surface that fills the stage, that the engine says so at the right
  moment, and where every file comes from.
- **It is not** the surface following the size of the stage when a
  panel opens or the window changes (GLB-028). The tests of this task
  look at the page as it opens.
- **It is not** what a person is told while the globe loads or when it
  fails (GLB-004). Until then the stage only marks the globe as busy,
  and hands a failure to the browser, which reports it.
- **It is not** how the globe is moved (GLB-005 onwards), what it looks
  like around the Earth, or what the engine says of its imagery on the
  globe (GLB-015): the engine's own way with the mouse, its sky and its
  own mark in the corner are as the engine has them, and no test of
  this task holds them. Neither is the view the globe opens with: the
  engine fits the Earth to the height of the surface, so that on a
  phone held upright the Earth is wider than the stage ("What the
  planner tried"). That is settled with GLB-003.

## Design in short

The new module, in full but for its comments:

    import {
      buildModuleUrl,
      CesiumWidget,
      ImageryLayer,
      TileMapServiceImageryProvider,
    } from '@cesium/engine'
    import '@cesium/engine/Source/Widget/CesiumWidget.css'
    import type { Start } from './Globe.tsx'

    const PICTURES_OF_THE_EARTH = 'Assets/Textures/NaturalEarthII/'

    export const start: Start = (surface, listener) => {
      const pictures = ImageryLayer.fromProviderAsync(
        TileMapServiceImageryProvider.fromUrl(buildModuleUrl(PICTURES_OF_THE_EARTH)),
      )
      const widget = new CesiumWidget(surface, { baseLayer: pictures, requestRenderMode: true })
      const { scene } = widget

      const askNoMore = scene.postRender.addEventListener(() => {
        if (scene.globe.tilesLoaded) {
          askNoMore()
          queueMicrotask(listener.drawn)
        }
      })

      return () => {
        const picture = scene.canvas.getContext('webgl2')
        widget.destroy()
        picture?.getExtension('WEBGL_lose_context')?.loseContext()
      }
    }

The stage, where the browser can draw:

    const [drawn, setDrawn] = useState(false)

    if (draws) {
      return (
        <div className={styles.globe} aria-busy={!drawn}>
          <Globe
            load={loadTheEngine}
            onDrawn={() => {
              setDrawn(true)
            }}
            onFailed={reportError}
          />
        </div>
      )
    }

The page, which hands the way to load down through the application:

      const { start } = await import('./globe/earth.ts')
      return start
    }
    ...

## What the trial measured and settled

- **The widget of the engine, with the pictures that come with it.**
  The project has the package `@cesium/engine` and no other of the
  engine's. Its `CesiumWidget` draws the globe; its
  `TileMapServiceImageryProvider` reads the Natural Earth II pictures
  that are among the engine's files in the site since GLB-022. In the
  page as it was built, the Earth was in the stage about three seconds
  after the page was opened on the planner's machine, with nothing on
  the console.
- **The widget must be told which pictures to use.** Left to itself
  the engine asks a service of its maker for pictures, on another
  computer and with an account. A planted defect that leaves
  `baseLayer` out is found by the test that nothing is asked of
  another computer.
- **The module writes no address.** The folder of the pictures is
  given to the engine's own `buildModuleUrl`, which puts it under the
  address the engine was told (GLB-025). A unit test holds that
  `earth.ts` has no address with the name of a computer in it, and
  that no other module of the application brings the engine in.
- **The engine draws when something has changed, and not sixty times a
  second** (`requestRenderMode: true`). A browser test has the page
  count the pictures its 3D pictures are told to draw. With its last
  piece arrived the engine draws the complete picture, which is when
  the module says that the Earth is drawn, and then that same picture
  once more, of its own accord: one picture after the moment, 9 of 9
  times in the planner's measurement, and none after that. The test
  holds that no more than one is drawn in the second and a half after
  the moment. A planted defect that lets the engine draw all the time
  drew 35 to 62 in that time and is found every time.
- **The moment is noted in the page, not seen from outside.** A test
  learns that the globe is no longer busy by asking again and again,
  up to a second late, and later still on a busy machine. The trial's
  first test looked at what had arrived and what was drawn when it
  learned it. When the planted defects were run a second time, with
  another run of tests beside them, the engine that says "drawn" with
  its first picture passed that test: by the time the test looked,
  the pictures had arrived and the engine was quiet. So the page now
  notes, at the moment the stage stops being busy, which files have
  arrived and how many pictures were drawn (a `MutationObserver` in a
  script the test adds to the page), and the test reads those notes.
  The three defects of timing were then each tried five times against
  the new test and found five times: the two that say it too early
  with no picture of the Earth arrived at the moment, the one that
  draws all the time by its count. The test passed 12 of 12 runs with
  the module as it is.
- **"Drawn" is one question, asked after every picture**: whether a
  piece of the Earth is still waiting (`scene.globe.tilesLoaded`, in
  `scene.postRender`). The trial first asked a second question too,
  whether the pictures themselves are ready; a planted defect that
  left it out was found by no test, the engine's own code shows why
  (a piece whose picture is not there yet is still waiting), and the
  question was taken out. Planted defects that say "drawn" with the
  first picture, or as soon as the pictures are known, are found: the
  pictures have not arrived then.
- **It is said when the engine has finished that picture**
  (`queueMicrotask`). After `postRender` the engine still has work to
  do for the same picture. A listener may stop the engine there and
  then, as the stage could one day, and an engine that is stopped in
  the middle of a picture fails. A browser test does just that; a
  planted defect that says it at once is found by it.
- **It is said once.** The module stops asking when it has said it.
  The component would tell nobody a second time anyway (GLB-029); the
  browser test holds the module itself to it, with an engine that is
  made to draw again.
- **Stopping gives the browser its 3D picture back.** Taking the
  widget away (`widget.destroy()`) does not: the browser keeps the
  picture until it tidies up, and it keeps only so many for a page,
  sixteen in the browser of the tests. With one more it takes the
  oldest away, which is the globe of the page, and says so on the
  console. So the module asks the browser to take the picture back
  (`WEBGL_lose_context`). The browser test starts and stops twenty
  engines in a row; planted defects that keep the picture, leave the
  widget, or do not stop at all are each found by it.
- **That test has 90 seconds.** In the first trial on GitHub it took
  8.9 seconds on the Linux machine and 18.5 on the Windows machine, of
  the 30 a browser test has, and the next slowest test 10.7 seconds on
  Windows. How fast GitHub's Windows machine is differs from run to
  run (the backend tests took it 76.7 seconds in one trial of this
  night and 134.8 in another), so the planner gave this one test
  three times the time (`test.setTimeout(90_000)`) and ran the trial
  again. The test holds what the engine does, not how fast a machine
  is; no other test's time is changed.
- **The engine comes after the page.** The page's own script is
  229.74 kB as built. The engine is a script of its own,
  `assets/earth-<hash>.js`, of 3,920.44 kB (1,041.4 kB as it travels,
  compressed), with a style sheet of 1.76 kB, and the page fetches
  both when the stage shows the globe. A browser test holds the
  script back and finds the page there and working. In a browser that
  gives no 3D picture neither is asked for.
- **The build says that a script is larger than 500 kB.** That is
  Vite's advice, not a failure: the build gate passes, and the engine
  is a script of its own already. How the engine reaches a visitor
  faster is a question for Phase 13.
- **The style sheet of the engine's widget is needed.** It gives the
  widget and its drawing surface the size of the element they are in.
  A planted defect that leaves it out is found: the surface does not
  fill the stage. The stage gives the globe its room with a rule of
  its own (`.globe` and the element in it fill the stage).
- **Busy until drawn.** The stage keeps one thing in mind, whether the
  Earth is drawn, and says it with `aria-busy` on the element around
  the globe. It is what the browser tests wait for, and what GLB-004
  will show a person. The main landmark is named "Globe" as before.
- **The unit tests cannot start the real engine.** Their environment
  gives no 3D picture, and the engine says so with an error. So the
  stage is handed how the engine is loaded (the stand-in in the unit
  tests, the real module in the page), and the two test files that
  start the whole page replace the module that starts the engine. The
  real engine is tested where it can run: in the browser tests.
- **What the engine brings along is left as it is**: its own mark in a
  corner of the globe, with a link; its sky; and its way of being
  moved with the mouse. None is held by a test of this task. What the
  globe must say of its pictures and of the engine, and where, is
  GLB-015. The terms of the Natural Earth II pictures are not recorded
  by the project by themselves yet: reading the terms of every set of
  pictures is GLB-012, and this plan states nothing about them. The
  licence of the engine goes with the site (FND-047).

### Why

The tester ran the planner's planted defects against the pull request.

that is drawn (in `GlobeStage.tsx`, `onFailed` also calls

fail for that stage, every time.

The cause is in the tests, not in the stage. The stage keeps state:
whether the globe is drawn. Outside `act` React does what it is asked
for a moment later, with `setImmediate`, and the stand-in for the
engine waits for a moment of its own, with `setTimeout`, before the
test goes on. The two come in no fixed order. A test that looked at
the stage straight after the stand-in's moment looked, in most runs,
before React had shown what the stage wrongly asked for, and passed.
With the stage as it is, nothing is asked of React at that point, so
no test of the pull request can fail by this: the 516 unit tests
passed in every run. What it weakened is what two of them prove.

Three tests hold that the stage still says busy after an engine has
arrived or failed. They now have that happen inside `act`
(`andReactIsDone`), so they look when React is done. No test is added
or taken away, and no assertion changes.
