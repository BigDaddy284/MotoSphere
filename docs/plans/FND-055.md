# FND-055 – The unit tests that start the page leave nothing of it running

**Phase:** 1 – Foundation
**Track:** B (see `TASKS.md`, "Two tracks")
**Depends on:** GLB-025 (merged)
**Base branch:** `main`
**Read first:** `CLAUDE.md` §3 and §18, `docs/WORKFLOW.md`, `TASKS.md`
("Two tracks" and the entry of this task), `frontend/src/main.tsx`,
`frontend/src/main.test.tsx`, `frontend/src/globe/engineAddress.test.ts`,
`frontend/src/test/setup.ts`

## Objective

Each of the two unit tests that start the whole page ends only when
React has nothing left to do, so that no work of the page can run after
the test's document is gone.

## Why

A run for `main` failed on GitHub's Linux machine although every test
passed (run 46006701452, for `e39aab3`, a commit that changed only
`TASKS.md` and `PROGRESS.md`). The frontend unit tests ended with
`Tests  387 passed (387)` and `Errors  1 error`:

```
Vitest caught 1 unhandled error during the test run.
ReferenceError: window is not defined
 > node_modules/react-dom/cjs/react-dom-client.development.js:19555:13
 > Immediate.performWorkUntilDeadline node_modules/scheduler/cjs/scheduler.development.js:45:48
This error originated in "src/globe/engineAddress.test.ts" test file.
```

The gate failed with exit code 1 (`18 of 19 gates passed.`,
`Tests: 3179 passed, 0 failed, 0 skipped.`). The Windows job of the same
run passed all 19 gates, and so did both machines in the run before it,
for the same code.

The cause is in a test, not in the application. Two unit tests start the
whole page by bringing in `src/main.tsx`:

- `entry point > renders the application into the root element`
  (`src/main.test.tsx`, since FND-010);
- `the application > has told the engine by the time it has started`
  (`src/globe/engineAddress.test.ts`, since GLB-025, as the planner
  wrote it).

`main.tsx` calls `createRoot(...).render(...)`. React does not show the
page inside that call. It puts the work in a queue (with
`setImmediate`) and does it a moment later, and what follows from
showing the page (the effects) a moment after that. The test of GLB-025
did not wait for any of it: it ended with React's work still in the
queue. The test after it is the last of its file and takes no time to
speak of, so the file ended, the test runner took the test's document
away, and React's work ran afterwards. Line 19555 is the first line of
what React does after it has shown a page; it reads `window`, which was
gone.

Whether the work runs before the document is taken away or after is a
matter of a few moments either way. Nearly always it runs before, and
nothing is seen. That is why the task passed everywhere before it was
merged, and why running a test again proves nothing here.

The test of FND-010 waits until the heading is on the page, so the page
is shown before it ends. What follows from showing it can still be
waiting then. That has not failed a run, but nothing rules it out.

## What this task is, and what it is not

- **It is** a change to two tests, one in each of the two files: each
  starts the page inside React's `act`, which comes back only when
  React's queue is empty, and then looks at the page at once.
- **It is** a section in `TESTING.md` that says so for every unit test
  that starts the page from now on, and a line in `CHANGELOG.md`.
- **It is not** a change to the application: `main.tsx` is as it was.
- **It is not** a second try for a test, a longer wait or a pause: none
  of those rules the fault out.
- **It is not** a guard for all unit tests that fails a file which ends
  with React's work waiting. That is a task of its own (FND-056).

## Design in short

```ts
await act(async () => {
  await import('./main.tsx')
})
```

`act` is React's own tool for tests, handed on by Testing Library
(`@testing-library/react`, which the project has; `setup.ts` already
brings it in, and its `render` uses `act` for every component test).
Work that React is given inside `act` does not go to the queue of
`setImmediate`. It is kept and done before `act` comes back, with all
that follows from it, and with all that follows from that. When `act`
has come back, React has nothing waiting.

So that a start outside `act` cannot come back unnoticed, each test
looks at the page **at once** after `act`:

- `main.test.tsx` asks for the heading with `screen.getByRole`, where it
  waited for it with `await screen.findByRole`. Outside `act` the page
  is not shown yet at that line, and the test fails.
- `engineAddress.test.ts` expects the root element not to be empty
  (`expect(root).not.toBeEmptyDOMElement()`). Outside `act` it is still
  empty at that line, and the test fails.

Both fail every time then, not one run in many: that is what the two
prove-it steps show.

In `engineAddress.test.ts` the root element is taken out of the document
right after `act` and before anything is expected. It was taken out as
the last line of the test, which a failed expectation skips; the test
after it expects a document without a root element and would then fail
too, for a reason that is not its own.

## What is left as it is

- `frontend/src/main.tsx` and every other file of the application.
- The second test of each file (`fails with a clear message when the
  root element is missing`, `has told the engine even when it cannot
  start`): `main.tsx` throws there before it calls React, so React is
  given no work.
- All component tests: they show their component with `render` of
  Testing Library, which uses `act` by itself.
- The work the test's document itself has waiting when these two files
  end, one piece for each style sheet `main.tsx` brings in. It is not
  React's. jsdom drops what a document has waiting when the document is
  taken away (`_queueATask` in its `Document-impl.js`: "Queue
  document-associated work, discarding it on destruction").
- `frontend/src/test/setup.ts` and `frontend/vitest.config.ts`.

## Existing tests that change, and why

Two tests change. None is taken out, none is weakened and no test is
added; the frontend unit tests are 387 as before.

1. `src/main.test.tsx`, `renders the application into the root
   element`: `await import('./main.tsx')` is put inside `act`, and
   `await screen.findByRole(...)` becomes `screen.getByRole(...)`. It
   still expects the heading with the application's name to be visible.
   It now expects it at once, which is more than before.
2. `src/globe/engineAddress.test.ts`, `has told the engine by the time
   it has started`: `await import('../main.tsx')` is put inside `act`;
   the root element is taken out right after; one expectation is added
   (the root element is not empty); the expectation of before (the
   address is told) stays.

The import line of each file gains `act`.
